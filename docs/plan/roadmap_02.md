# 타운빌더 개발 로드맵 02 — 완성도 (완료)

> **상태: 완료 (2026-09-02).** Phase 1~6을 모두 마쳤다. 이 문서는 기록으로 남긴다.
> 이후 계획은 `docs/plan/roadmap_03.md`에 있다.
>
> - 각 Phase의 산출물과 검증 결과: `docs/state/`
> - 이 로드맵에서 내린 결정: `docs/adr/` 0008~0011
> - 최종 상태: 단위 테스트 700개, 봇 통과 플레이로 세 시드 모두 마을 레벨 10 도달(약 5분)

- **선행**: `docs/plan/roadmap_01.md` (MVP, 완료)
- **기획서**: `docs/plan/project.md`

## 목표

MVP는 기획서의 모든 시스템이 **동작한다**는 것을 보였다. 이 로드맵의 목표는 그것을
**남에게 보여줄 수 있는 상태**로 만드는 것이다. 새 시스템을 늘리지 않고, 지금 있는 것을
저장되고·보이고·들리고·이해되게 만든다.

지금 상태에서 가장 크게 벌어져 있는 세 가지:

| 항목 | 현재 | 이 로드맵의 목표 |
|---|---|---|
| 지속성 | 새로고침하면 마을이 사라진다 | 자동 저장, 이어하기 |
| 표현 | 전부 색상 도형, 무음 | 스프라이트, 소리와 이펙트 |
| 이해 | 조작을 하단 한 줄로만 알린다 | 처음 켠 사람이 루프를 스스로 찾아간다 |

**콘텐츠 확장(동굴·다중 맵·전투·NPC 직업)은 이 로드맵에 넣지 않는다.** 기획서 9절의
확장 아이디어이며 로드맵 03의 후보다. 단 Phase 6은 경계에 걸치므로 그 절에서 따로 다룬다.

## 0. 진행 원칙

로드맵 01의 원칙을 그대로 잇는다.

- **수직 슬라이스 우선** — 각 Phase가 끝날 때마다 브라우저에서 눈에 보이는 결과물이 남는다.
- **테스트 동반** — 순수 로직은 기능 직후 단위 테스트를 작성한다. 현재 523개가 통과한다.
- **되돌리기 비싼 결정은 ADR** — `docs/adr/`에 배경·결정·검토한 대안·예상되는 결과를 남긴다.
- **Phase 단위 커밋** — 산출물이 동작하는 시점에 commit 및 push 한다.
- **Phase 종료 시 상태 기록** — `docs/state/날짜_시간.md`에 한 일과 다음 할 일을 남긴다.

여기에 이 로드맵에서 새로 지킬 것 두 가지를 더한다.

- **도형 렌더링을 지우지 않는다.** 스프라이트를 넣어도 종류별 도형 그리기 함수는 폴백으로
  남긴다. 이미지 로딩 실패, 로딩 중 첫 프레임, 그리고 **헤드리스 테스트**가 그 위에서 돌기
  때문이다. 지금 렌더러 테스트 30여 개가 가짜 컨텍스트에 기록된 도형을 검증한다.
- **저장 형식은 버전을 갖는다.** 블록 타입과 아이템 타입이 숫자·문자열 리터럴이라 값이
  바뀌면 예전 저장이 조용히 잘못 읽힌다. 첫 저장부터 버전 필드를 넣고 마이그레이션 정책을
  ADR로 정한다.

## 1. 의존 관계

```
Phase 1 세이브/로드
   ├─ Phase 2 스프라이트 아트 ── Phase 3 사운드와 이펙트
   │                                   └─ Phase 5 첫 플레이 안내
   └─ Phase 4 조작·카메라 다듬기 ──────┘
                                        └─ Phase 6 밸런스 2차
```

Phase 2·3·4는 서로 독립이므로 순서를 바꿔도 된다. Phase 5는 앞의 표현 작업이 끝난 뒤라야
"무엇을 보고 이해하게 할지"를 정할 수 있고, Phase 6은 마지막에 전체를 놓고 조정한다.

**Phase 1을 맨 앞에 둔 이유**: 저장은 뒤로 갈수록 붙이기 어려워질 것처럼 보이지만, 실제로는
반대다. Phase 2~5는 **표현과 안내**라 지속 상태를 거의 늘리지 않는다(Phase 5의 안내 진행도
플래그 정도). 반면 저장이 없으면 이후 모든 Phase의 확인이 "새로 시작해서 다시 모으기"가 된다.
지금 MVP 확인에 매번 3분씩 자원을 모아야 했던 것이 그 비용이다.

## Phase 1 — 세이브/로드

**목적**: 새로고침하고 이어서 플레이할 수 있게 한다.

### 무엇을 저장하는가

결정적 생성 덕분에 **전부 저장할 필요가 없다.** 지형과 자원 노드 배치는 시드에서 재현되므로
(`generateTerrain`, `ResourceField`가 `hashNoise` 기반), 저장할 것은 **시드 + 그 뒤의 변경분**이다.

| 대상 | 저장 방식 |
|---|---|
| 지형 | 시드 + `heights`/`types` 두 `Uint8Array` (파고 쌓은 결과가 담긴다) |
| 자원 노드 | 시드 + 노드별 내구도·리스폰 잔여 시간 (배치 자체는 재현) |
| 플레이어 | 위치, 도구 슬롯과 등급 |
| 인벤토리·창고 | 슬롯 배열 |
| 건물 | 목록(블루프린트 id, 좌표, 건축 잔여 시간) — 점유 맵은 로드 시 재구성 |
| 주민 | 목록(번호, 집 건물 번호, 위치) — 배회 상태는 초기화해도 무방 |
| 요청 | 열린 요청 목록, 완료 수, 다음 요청 타이머 |
| 마을 | 레벨, 누적 경험치 |

**주의점**: `Buildings`의 점유 Map과 `Population`의 집 참조가 건물 번호로 엮여 있다.
로드는 "상태를 그대로 되살리는 것"이 아니라 **저장값으로 객체를 다시 조립하는 것**이어야
한다 — 파생 자료구조(점유 맵)를 저장하면 저장과 파생이 어긋난 상태를 만들 수 있다.

### 작업

- 저장 형식 정의(`src/core/save.ts`): 버전 필드, 직렬화/역직렬화 순수 함수
- 저장소 어댑터(`src/sim/SaveStore.ts`): localStorage 읽기/쓰기, 용량 초과·손상 처리
- 자동 저장: 고정 간격(예: 30초)과 주요 사건(건축 완공, 레벨업) 시점
- 수동 저장/불러오기/새로 시작 UI — 대사창 없이 하단 바나 작은 메뉴로
- 로드 실패 시 새 게임으로 안전하게 떨어지기(손상된 저장을 지우지 않고 보존)

### 테스트

- 왕복: 저장 → 로드 → 모든 관측 가능한 값이 같다(지형 높이, 인벤토리, 건물, 주민, 요청, 레벨)
- 지형 변경분이 보존된다(판 구덩이와 쌓은 언덕이 그대로)
- 건물 점유 맵이 로드 후 재구성된다(같은 자리에 다시 지을 수 없다)
- 버전이 다른 저장을 거부하거나 마이그레이션한다
- 손상된 JSON·잘린 배열을 만나도 예외로 죽지 않는다
- **봇 통과 플레이 중간에 저장/로드해도 이어서 레벨 5에 도달한다** (`playthrough` 테스트 확장)

**완료 기준**: 마을을 키우다 새로고침해도 그대로 이어진다. 손상된 저장으로 게임이 죽지 않는다.

**ADR 후보**: 저장 위치(localStorage vs IndexedDB), 형식(JSON vs 이진), 버전 마이그레이션 정책,
슬롯 개수(단일 슬롯 vs 다중).

## Phase 2 — 스프라이트 아트 교체

**목적**: 색상 도형을 이미지로 바꿔 화면이 게임처럼 보이게 한다.

### 작업

- 에셋 파이프라인: 이미지 로딩, 아틀라스(한 장에 여러 스프라이트), 로딩 진행 표시
- 타일 스프라이트: 지형 윗면과 측면 — **타일 64×32, 레이어 16px 규약(ADR 0002)에 맞춘 치수**
- 오브젝트: 나무(성장/손상 단계), 광맥 2종, 건물 5종
- 캐릭터: 플레이어와 NPC, 방향 4종 + 걷기/타격 동작
- 도형 폴백 유지: 로딩 전·실패 시·테스트에서 지금 코드가 그대로 동작해야 한다

### 주의점

- **이미지 로딩은 비동기다.** 지금 렌더러는 동기 그리기만 가정한다. 로딩 중 첫 프레임을
  도형으로 그리고 이미지가 준비되면 갈아타는 구조가 필요하다.
- **깊이 정렬 규약이 스프라이트에서도 성립해야 한다.** 스프라이트가 타일 경계를 넘어 그려지면
  (예: 높은 나무) 지금의 `(x + y)` 정렬로는 겹침이 어긋날 수 있다. ADR 0002가 한계로 적어 둔
  지점이며, 건물은 ADR 0006에서 점유 영역 기준으로 이미 해결했다. 나무·NPC도 같은 방식으로
  기준점을 정해야 한다.
- 아트 리소스 자체를 어디서 구할지(직접 제작/에셋 팩/생성)는 이 문서의 결정 범위 밖이다.

### 테스트

- 이미지가 없을 때 도형으로 그린다(기존 렌더러 테스트가 그대로 통과)
- 로딩 실패해도 게임이 계속 돈다
- 스프라이트 좌표 계산(아틀라스 슬라이싱)의 경계값
- 그리기 순서가 스프라이트에서도 지형과 어긋나지 않는다

**완료 기준**: 스크린샷만 봐도 무엇을 하는 게임인지 읽힌다. 이미지를 지워도 게임은 돈다.

**ADR 후보**: 아틀라스 구성과 좌표 규약, 도형 폴백을 유지하는 방식, 애니메이션 표현 방식
(프레임 시퀀스 vs 상태 보간).

## Phase 3 — 사운드와 이펙트

**목적**: 행동에 반응이 있게 한다. 지금은 완전히 무음이다.

### 작업

- 오디오 재생기: Web Audio 기반, **첫 사용자 입력에서 잠금 해제**(브라우저 자동재생 정책)
- 효과음: 파기·벌목·채굴·건축 착공·완공·이주·레벨업·요청 완료·거절
- 배경음: 낮은 볼륨 루프 한 트랙, 켜고 끄기
- 볼륨 설정과 저장(Phase 1의 저장에 얹는다)
- 시각 이펙트 보강: 채집 시 파편, 자원 획득 표시, 레벨업 강조

### 주의점

- **소리는 게임 루프가 아니라 사건에서 나온다.** `Game`이 이미 알림을 `drainNotices`로 쌓아
  UI가 꺼내 가는 구조이므로, 같은 통로로 소리를 붙이면 규칙과 표현이 계속 분리된다.
- 무음 환경(테스트, 자동재생 차단)에서 예외 없이 조용히 넘어가야 한다.

### 테스트

- 사건 → 재생 요청 매핑(가짜 재생기로 호출만 검증)
- 잠금 해제 전에는 재생을 시도하지 않는다
- 볼륨 0이면 재생하지 않는다
- 오디오가 없는 환경에서 게임이 죽지 않는다

**완료 기준**: 나무를 베면 소리가 나고, 레벨업이 귀로도 전달된다. 소리를 꺼도 게임이 정상이다.

**ADR 후보**: 오디오 스택(Web Audio vs `<audio>`), 에셋 형식과 용량 예산.

## Phase 4 — 조작·카메라 다듬기

**목적**: MVP를 확인하며 걸렸던 마찰을 없앤다. 아래는 실제로 겪은 것들이다.

### 작업

- **구역 경계 시각화** — 지금은 커서 안내의 "(잠김)"이 유일한 단서다(ADR 0007이 남긴 항목).
  지면에 옅은 경계선이나 잠긴 구역의 채도 낮추기 등으로 눈에 보이게 한다.
- **연속 채집** — 지금은 클릭을 반복해야 한다. 누르고 있으면 이어서 타격하게 한다.
- **키보드 조작 방향** — 그리드 축에 직접 매핑돼 있어 D가 화면 오른쪽-아래로 간다(ADR 0004가
  남긴 항목). 화면 기준 매핑을 옵션으로 둘지 판단한다.
- **카메라** — 추적/자유 전환이 걸으면 켜지고 드래그하면 꺼지는 방식이다. 경계 밖으로 나가지
  않게 제한하고, 줌 한계와 속도를 다시 본다.
- **선택 상태 표시** — 건축 모드에서 어떤 블루프린트가 골라져 있는지 커서 근처에서도 보이게 한다.
- **두 레이어 계단 모호함** — `LAYER_HEIGHT`가 타일 높이의 절반이라 두 칸 올라간 열이 한 타일
  뒤 열과 겹쳐 보인다(ADR 0002가 남긴 항목). 실제로 혼란을 주는지 판단하고, 준다면 값 변경을
  검토한다. **이 값은 ADR 0002의 개정 사항이므로 바꾼다면 ADR을 갱신한다.**

### 테스트

- 연속 채집이 휘두르기 쿨다운을 지킨다
- 카메라가 맵 밖으로 나가지 않는다
- 구역 경계 판정과 표시 대상이 일치한다

**완료 기준**: 처음 잡은 사람이 조작 때문에 멈추지 않는다.

**ADR 후보**: 키 매핑 규약 변경 시 ADR 0004 개정, `LAYER_HEIGHT` 변경 시 ADR 0002 개정.

## Phase 5 — 첫 플레이 안내

**목적**: 처음 켠 사람이 "채집 → 건축 → 주민 → 레벨"의 루프를 스스로 찾아가게 한다.

### 제약

기획서 5.4·7절이 **대사창과 컷신을 명시적으로 배제**한다. 따라서 튜토리얼 창을 띄우는 방식은
쓸 수 없다. 안내는 **토스트·아이콘·강조**만으로 해야 한다 — 이 제약이 이 Phase의 설계를
좌우한다.

### 작업

- 첫 목표 제시: 마을 레벨 게이지 옆에 "지금 할 일" 한 줄(예: "나무를 베어 목재를 모으세요")
- 상황 기반 힌트: 자원을 충분히 모으면 "B로 집을 지을 수 있습니다" 같은 안내를 한 번만
- 첫 채집·첫 건축·첫 이주 시점의 강조 연출
- 안내 진행도 저장(Phase 1) — 두 번째 플레이에는 반복하지 않는다
- 조작 안내 개선: 지금 하단 한 줄에 모든 키가 나열돼 있다. 상황에 맞는 것만 보이게 한다

### 테스트

- 안내 조건 판정(무엇을 언제 보여줄지)이 상태만으로 결정된다
- 한 번 본 안내는 다시 나오지 않는다
- 저장/로드 후에도 진행도가 유지된다

**완료 기준**: 설명 없이 건네줘도 첫 집을 짓는다.

## Phase 6 — 밸런스 2차 (마을 레벨 10)

**목적**: 기획서 6절이 예로 든 "마을 레벨 10 달성"까지 진행을 늘린다. MVP는 5까지였다.

### 작업

- 레벨 6~10 임계값과 해금 설계 — `LEVEL_THRESHOLDS`와 `LEVEL_UNLOCKS` 확장
- 자동 플레이 봇으로 각 구간 소요 시간 측정(`test/playthrough.test.ts` 확장)
- 채집 속도·리스폰·자재 요구량 재조정
- 후반 구간이 반복 노동이 되지 않게 하는 장치 검토

### 이 Phase가 경계에 걸치는 지점

**레벨 10까지 늘리려면 해금할 것이 더 필요하다.** 지금은 블루프린트 5종·도구 3등급이 전부이고
레벨 5에서 모두 열린다. 레벨 6~10에 열 것이 없으면 숫자만 커지는 진행이 된다.

선택지는 둘이다.

1. **표현·편의 해금으로 채운다** — 건물 외형 슬롯(기획서 5.3의 후순위 항목), 창고 확장,
   이동 속도 증가 등. 이 로드맵의 성격에 맞는다.
2. **새 콘텐츠를 연다** — 새 블루프린트, 동굴 진입, NPC 직업. **로드맵 03의 영역이다.**

**Phase 6 착수 시점에 이 선택을 먼저 하고 ADR로 남긴다.** 2번을 고르면 이 Phase는 로드맵 03의
첫 Phase로 옮기는 편이 맞다.

### 테스트

- 봇이 레벨 10까지 막힘 없이 도달한다(여러 시드)
- 각 구간 소요 시간이 앞 구간보다 지나치게 길어지지 않는다

**완료 기준**: 처음 실행해서 레벨 10까지 막힘 없이 플레이된다.

**ADR 후보**: 레벨 6~10의 해금 성격(위 선택), 임계값 곡선.

## 2. 이 로드맵 범위 밖

기획서 8절의 MVP 제외 항목과 9절 확장 아이디어는 **로드맵 03**에서 다룬다.

- 동굴 별도 맵과 다중 맵 이동 (ADR 0003이 "동굴은 별도 맵"으로 전제해 둔 방향)
- 전투·몬스터 침입 이벤트
- NPC 직업 배정과 마을 자동 생산
- 건물 커스터마이징(외형 슬롯) — 단 Phase 6의 선택지 1번에 걸치면 앞당길 수 있다
- 날씨·계절·낮밤 사이클
- 지형 조각 콘텐츠(정원, 연못)

## 3. 미해결 항목

- ~~**아트 리소스 조달**~~ — 해결. 외부 파일 대신 **코드로 생성해 캐시**한다(ADR 0009).
- ~~**사운드 리소스 조달**~~ — 해결. 같은 방식으로 **Web Audio 합성**(ADR 0010).
- ~~**저장 슬롯 정책**~~ — 해결. 단일 슬롯 + localStorage(ADR 0008).
- **배포** — 미해결. "보여줄 수 있는 상태"가 됐으나 실제로 보여줄 경로가 아직 없다.
  정적 빌드라 호스팅 자체는 간단하다. **로드맵 03의 첫 항목 후보다.**
