# 타운빌더 개발 로드맵 03 — 콘텐츠 확장

- **선행**: `docs/plan/roadmap_01.md` (MVP, 완료), `docs/plan/roadmap_02.md` (완성도, 완료)
- **기획서**: `docs/plan/project.md`
- **현재 상태**: 단위 테스트 700개, 봇 통과 플레이로 세 시드 모두 마을 레벨 10 도달(약 5분)

## 목표

로드맵 01은 기획서의 시스템이 **동작한다**는 것을 보였고, 로드맵 02는 그것을 **보여줄 수 있는
상태**로 만들었다. 그런데 아직 보여줄 **주소가 없고**, 보여준 뒤에 **더 할 것이 없다**.

이 로드맵의 목표는 두 가지다.

| 항목 | 현재 | 이 로드맵의 목표 |
|---|---|---|
| 접근 | 로컬에서 `npm run dev`로만 돌아간다 | 링크를 열면 게임이 뜬다 |
| 폭 | 맵 하나, 낮만 있고, 마을은 플레이어가 없으면 멈춘다 | 갈 곳이 늘고, 시간이 흐르고, 마을이 스스로 돌아간다 |

로드맵 02가 범위 밖으로 미뤄 둔 항목들(기획서 8절 제외 항목과 9절 확장 아이디어)이 여기 들어온다.
**ADR 0011이 "진짜 새로움은 로드맵 03이 맡는다"고 적어 둔 자리다.**

---

## 0. 진행 원칙

로드맵 01·02의 원칙을 그대로 잇는다.

- **수직 슬라이스 우선** — 각 Phase가 끝날 때마다 브라우저에서 눈에 보이는 결과물이 남는다.
- **테스트 동반** — 순수 로직은 기능 직후 단위 테스트를 작성한다.
- **되돌리기 비싼 결정은 ADR** — 배경·결정·검토한 대안·예상되는 결과를 남긴다.
- **Phase 단위 커밋**, **Phase 종료 시 `docs/state/날짜_시간.md`에 상태 기록**.
- **도형 렌더링을 지우지 않는다** — 새로 넣는 것(동굴 벽, 몬스터, 직업 표시)도 도형 폴백을 갖는다.
  헤드리스 테스트가 그 위에서 돈다.

여기에 이 로드맵에서 새로 지킬 것 세 가지를 더한다.

- **저장 형식이 여러 번 바뀐다는 것을 전제로 시작한다.** ADR 0008은 "버전이 다르면 읽지 않는다"로
  정했고 지금까지 `SAVE_VERSION = 1`이 한 번도 오르지 않아 그 정책이 시험된 적이 없다. 이 로드맵은
  **다중 맵(Phase 1)·시각(Phase 3)·직업과 외형(Phase 4·6)** 세 번에 걸쳐 형식을 바꾼다. 매번 올리고
  거절하면 플레이어의 마을이 세 번 날아간다. **Phase 1 착수 시점에 마이그레이션 정책을 정하고
  ADR 0008을 개정한다.**
- **에셋은 계속 코드로 만든다.** 스프라이트는 코드 생성(ADR 0009), 소리는 Web Audio 합성(ADR 0010)이
  규약이다. 동굴·몬스터·직업 표현도 같은 길로 간다. 이 방식이 버티지 못하는 지점이 오면 그때
  ADR로 판단한다(3절 미해결 항목).
- **봇이 새 시스템을 실제로 쓰게 만든다.** 로드맵 02 Phase 6에서 봇이 평탄화를 하지 않아 12분에
  레벨 3에 머물렀고, 그것을 고치자 5분에 레벨 10이 됐다. 맵 전환·직업 배정·야간 방어도 마찬가지다.
  **봇이 쓰지 않는 시스템은 측정되지 않는다.**

## 1. 의존 관계

```
Phase 0 배포 ─────────────────────────────── (독립. 언제 해도 되지만 먼저 하면 이후가 계속 검증된다)

Phase 1 다중 맵 기반
      └─ Phase 2 동굴과 희귀 광물 ──────────┐
                                            │
Phase 3 낮과 밤                             │
      ├─ Phase 4 NPC 직업과 자동 생산       │
      └─ Phase 5 몬스터 침입과 방어 ────────┘
                                            │
Phase 6 건물 커스터마이징 (독립)            │
                                            ▼
                                   Phase 7 밸런스 3차
```

- **Phase 0을 맨 앞에 둔 이유**: 가장 싸고, 한 번 해 두면 이후 모든 Phase가 실제 배포본에서 확인된다.
  로컬에서만 되는 것과 배포본에서 되는 것이 다른 종류의 실패(경로, 자산 로딩, 저장 키)를 낳는다.
- **Phase 1이 Phase 2의 전제인 이유**: 지금 `Game`은 `terrain`·`resources`를 각각 하나씩 `readonly`
  필드로 들고 있고(`src/sim/Game.ts:110`, `:114`), 저장 형식도 한 벌만 담는다(`src/core/save.ts`).
  동굴을 넣기 전에 이 전제를 걷어내야 한다. **먼저 구조를 열고, 그 다음에 콘텐츠를 넣는다.**
- **Phase 3이 Phase 4·5의 전제인 이유**: 기획서 5.4는 NPC가 "정해진 시간대에 배회"한다고 하고,
  9절의 몬스터 침입은 밤에 오는 것이 자연스럽다. 시간축이 없으면 둘 다 어색한 형태가 된다.
- **Phase 5가 Phase 2에 의존하는 이유**: 방어 시설을 지을 상위 자재가 필요하다.
- Phase 6은 어디에 넣어도 되는 가장 싼 Phase다. 일정이 밀리면 **가장 먼저 덜어낼 항목**이다.

## Phase 0 — 배포

**목적**: 링크 하나로 열리게 한다. 로드맵 02가 "보여줄 수 있는 상태"를 만들었고, 여기서 실제 경로를 뚫는다.

### 작업

- GitHub Pages 배포(원격이 `github.com:seniya/game-dev1`이므로 가장 짧은 경로다)
- `vite.config.ts`에 `base` 설정 — 저장소 이름이 경로에 들어가므로 기본값으로는 자산이 404가 난다
- GitHub Actions 워크플로: main push 시 `npm ci && npm run build` 후 Pages에 배포
- `dev` → `main` 병합 정책 정하기(지금 작업 브랜치는 dev, 배포 기준은 main)
- README에 주소와 조작 요약

### 주의점

- **`dist/`가 `.gitignore`에 있다.** 산출물을 커밋하는 방식이 아니라 Actions에서 빌드해 배포한다.
- **`npm run build`가 이미 `tsc --noEmit`을 포함한다.** 타입 오류가 배포를 막는 구조라 그대로 쓴다.
- localStorage 저장 키가 origin 단위로 공유된다. 같은 도메인(`seniya.github.io`)에 다른 프로젝트를
  올리면 키가 겹칠 수 있으므로 접두어를 확인한다.

### 테스트

- `vite preview`로 `base` 경로에서 자산이 뜨는지 확인(수동)
- 배포본에서 저장/불러오기가 동작하는지 확인(수동)

**완료 기준**: 링크를 열면 게임이 뜨고, 새로고침해도 마을이 남는다.

**ADR 후보**: 배포 대상과 브랜치 정책.

## Phase 1 — 다중 맵 기반

**목적**: 게임이 "맵 하나"를 전제하지 않게 만든다. 이후 콘텐츠 확장 전부의 전제다.

### 현재 구조가 막는 것

| 지점 | 현재 | 필요한 것 |
|---|---|---|
| `Game` | `terrain`·`resources`를 하나씩 보유 | 맵 목록 + 현재 맵 |
| `save.ts` | `terrain`·`nodes`가 각각 한 벌 | 맵별 배열, 버전 2 |
| `zones.ts` | 맵 중심에서의 거리로 구역 판정 | 맵마다 다른 구역 규칙 |
| 렌더러·피킹·카메라 | 단일 `Terrain` 참조 | 현재 맵을 따라간다 |

### 작업

- 세계 모델 분리: **맵 하나 = 지형 + 자원 노드 + 구역 규칙**을 한 단위로 묶고, `Game`은 마을 상태
  (건물·주민·요청·창고·레벨)와 **현재 맵**을 든다
- 맵 간 이동 지점: 지상의 동굴 입구 타일 ↔ 동굴의 출구. 전환 시 플레이어 좌표 매핑
- 맵별 시드 파생 — 결정적 생성(`hashNoise`)을 유지하되 맵 id를 시드에 섞는다
- 저장 형식 v2: 맵 배열. **버전 정책의 첫 시험이다**(0절 참고)
- 마을 규칙의 경계: 건축·주민 이주·요청은 **지상 맵에서만**. 동굴에서 집을 못 짓게 하는 규칙을
  어디에 둘지 정한다(블루프린트 조건 vs 맵 속성)

### 주의점

- **로드는 "상태 복원"이 아니라 "저장값으로 재조립"이라는 로드맵 02 Phase 1의 원칙이 그대로 걸린다.**
  맵이 둘이 되면 파생 자료구조(건물 점유 맵)와 저장값이 어긋날 여지가 늘어난다.
- **맵을 떠날 때 버릴지 들고 있을지** 정해야 한다. 파고 쌓은 변경분은 어차피 저장해야 하므로
  들고 있는 편이 단순하다. 대신 메모리가 맵 수에 비례한다.
- **자동 저장과 맵 전환이 겹친다.** 전환 도중 저장되면 절반만 반영된 저장이 생길 수 있다.
- 봇 통과 플레이가 맵 전환을 알아야 한다.

### 테스트

- 맵 전환 왕복 후 지상 변경분이 보존된다(판 구덩이·지은 건물)
- 같은 시드로 같은 맵이 재현된다(맵별 결정성)
- v2 저장 왕복으로 두 맵의 모든 관측값이 같다
- v1 저장을 만났을 때 정한 정책대로 동작한다(마이그레이션 또는 안전한 거절)
- 동굴에서 건축이 거부된다
- 봇 통과 플레이가 맵을 오가며 레벨 10에 도달한다

**완료 기준**: 동굴 입구로 들어갔다 나오면 지상이 그대로다. 저장하고 새로고침해도 두 맵이 남는다.

**ADR 후보**: 세계/맵 모델, 저장 v2와 마이그레이션 정책(**ADR 0008 개정**), 맵 시드 파생 규약.

## Phase 2 — 동굴과 희귀 광물

**목적**: 갈 이유가 있는 두 번째 맵. 기획서 5.2의 "초원 → 숲 → 산악 → **동굴**"을 완성한다.

### 작업

- 동굴 지형 생성: 지상과 다른 규칙(막힌 암반 + 뚫린 통로). 결정적 생성 유지
- 희귀 광물 노드와 **고급 곡괭이 요구**(기획서 5.2의 도구 등급 체계를 상위로 한 칸 더)
- 희귀 자재로만 지을 수 있는 블루프린트 1~2종 — 갔다 온 보상이 마을에 남아야 한다
- 어둠: 플레이어 주변만 밝고 바깥은 어둡게. 조명 수단(도구/설비) 검토
- 동굴 입구는 산악 구역에 두고, 마을 레벨로 해금

### 주의점

- **높이맵은 오버행과 천장을 표현할 수 없다**(ADR 0003). 동굴을 "위에서 내려다본 통로"로 그리는
  규약이 필요하다 — 벽을 최대 높이 기둥으로 두면 자료구조를 바꾸지 않고도 표현된다. ADR 0003이
  전제해 둔 "동굴은 별도 맵" 방향과 어긋나지 않게 정한다.
- **어둠은 도형 폴백에서도 성립해야 한다.** 지금 렌더러 테스트가 가짜 컨텍스트에 기록된 도형을
  검증한다. 어둠이 스프라이트 전용 효과가 되면 테스트가 검증할 수 없는 영역이 생긴다.
- 스프라이트는 코드 생성(ADR 0009), 채굴음은 합성(ADR 0010) 규약을 그대로 따른다.

### 테스트

- 동굴 생성의 결정성과 연결성(입구에서 광맥까지 실제로 갈 수 있다)
- 도구 등급이 낮으면 희귀 광물 채굴이 거부된다
- 어둠 계산의 경계값(반경 안/밖, 경계 타일)
- 희귀 자재 블루프린트가 자재 없이는 거부된다

**완료 기준**: 동굴에 들어가 희귀 광물을 캐고, 지상에서 그것으로만 지을 수 있는 건물을 짓는다.

**ADR 후보**: 동굴 지형 표현 방식, 어둠/시야 규칙.

## Phase 3 — 낮과 밤

**목적**: 시간축을 넣는다. 그 자체로도 화면이 살고, Phase 4·5의 전제가 된다.

### 작업

- 게임 시간: 하루 길이, 시각 진행, 낮/저녁/밤/새벽 구간 판정
- 화면 색조 변화 — 시간대에 따라 전체 색을 얹는다
- 상단에 시각 표시(대사창 없이 아이콘·게이지로)
- 시간 기반 사건 훅 — Phase 4·5가 여기에 붙는다
- 밤에는 시야가 좁아진다(Phase 2의 어둠 장치를 재사용)
- 저장에 시각 포함(형식 변경 — 0절의 마이그레이션 정책 적용)

### 주의점

- **하루 길이를 봇 통과 플레이로 정한다.** 봇 기준 5분에 레벨 10인데 하루가 5분이면 밤을 한 번밖에
  못 보고, 30초면 정신없다. 측정으로 정할 값이다.
- **색조를 어디에 얹을지가 렌더링 구조 문제다.** 타일마다 색을 섞을지 화면 전체에 한 겹을 덮을지에
  따라 비용이 다르다. 성능 예산(60fps 유지)을 지켜야 한다.
- **날씨와 계절은 넣지 않는다.** 2절 참고.

### 테스트

- 시각 진행과 하루 경계 넘김(랩어라운드)
- 시간대 판정의 경계값
- 저장 왕복 후 시각이 유지된다
- 색조 계산이 경계에서 튀지 않는다

**완료 기준**: 해가 지고 뜬다. 화면만 보고 밤이 왔다는 것을 안다.

**ADR 후보**: 하루 길이와 시각 표현, 조명/색조 합성 방식.

## Phase 4 — NPC 직업과 자동 생산

**목적**: 기획서 9절. 마을이 플레이어 없이도 조금은 돌아가게 한다.

### 작업

- 직업 2~4종(농부·나무꾼·광부·대장장이 등)과 직업별 필요 시설
- 주민을 시설에 배정/해제 — 대사창 없이 아이콘과 목록으로(기획서 7절)
- 시간대별 행동: 낮에 일하고 밤에 집으로(Phase 3)
- 자동 생산물이 창고에 쌓인다
- 마을 레벨과 연계된 생산 속도

### 주의점

- **자동 생산이 채집 루프를 대체하면 게임이 없어진다.** 생산은 **보조**여야 한다 — 기본 자재를
  조금 보태는 정도이고, 상위 자재(철광석·희귀 광물)는 여전히 손으로 캔다.
- **주민 수가 예상보다 많다.** 측정에서 레벨 10에 주민 41명이었다. 전원이 직업을 가지면 생산이
  폭주한다. **직업 슬롯은 시설 수로 제한한다.**
- 요청 시스템과 겹치지 않게 한다 — "목재 5개를 주세요"를 자동 생산이 알아서 채우면 요청이 무의미해진다.

### 테스트

- 배정/해제 규칙(시설 없이 배정 거부, 슬롯 초과 거부)
- 생산량 누적과 창고 가득 참 처리
- 저장 왕복(직업 배정과 생산 진행도)
- 봇 통과 플레이에서 자동 생산이 진행 시간을 무너뜨리지 않는다

**완료 기준**: 시설을 짓고 주민을 붙이면 시간이 지나며 창고에 자원이 쌓인다. 그래도 직접 채집할 이유가 남는다.

**ADR 후보**: 직업/생산 모델, 자동 생산이 손 채집을 대체하지 않게 하는 규칙.

---

## Phase 5 — 몬스터 침입과 방어

**목적**: 기획서 9절의 "몬스터 침입 이벤트(스토리 없이 방어 미니게임 형태로)".

### 작업

- 침입 이벤트: 밤에 발생, 마을 레벨에 따라 빈도와 강도 증가
- 예고 알림(토스트와 아이콘) — 준비할 시간을 준다
- 몬스터 이동과 목표 설정
- 방어 수단: 울타리·망루 같은 방어 블루프린트(Phase 2의 상위 자재 사용) + 플레이어 도구 타격
- 실패 결과와 회복: **파괴가 아니라 손상과 수리**
- 성공 보상: 마을 레벨 경험치 또는 자재

### 주의점

- **이 Phase의 위험은 전투를 얼마나 깊게 만들 것인가다.** 도구로 때리는 것 이상으로 가면 체력·피격·
  적 AI가 통째로 새 시스템이 된다. 이 게임의 성격은 캐주얼 타운 빌더이고, 기획서도 "방어 미니게임
  형태"라고만 적었다. **착수 시점에 깊이를 먼저 정하고 ADR로 남긴다.**
- **되돌릴 수 없는 손실은 캐주얼 성격과 어긋난다.** 몇 시간 키운 마을이 하룻밤에 사라지면 캐주얼이
  아니다. 손상 → 자재로 수리가 기본 방향이다.
- 대사·컷신 없이 아이콘과 토스트로만 전달한다(기획서 7절).
- 침입 도중 자동 저장이 걸릴 수 있다.

### 테스트

- 침입 스케줄의 결정성(시드 기반)
- 방어 판정과 손상/수리 규칙
- 저장 왕복이 침입 도중에도 안전하다
- 봇 통과 플레이가 침입을 겪고도 레벨 목표에 도달한다

**완료 기준**: 밤에 몬스터가 오고, 울타리와 도구로 막는다. 막지 못해도 마을이 회복 가능하다.

**ADR 후보**: 전투의 깊이와 손실 규칙.

---

## Phase 6 — 건물 커스터마이징

**목적**: 기획서 5.3의 후순위 항목. ADR 0011이 "로드맵 03 후보로 남긴다"고 적어 둔 것이다.

### 작업

- 외형 슬롯: 색상·지붕 스타일 등 **소수 옵션 중 선택**(자유 조형은 하지 않는다 — 기획서 명시)
- 완공 건물 선택 → 외형 교체 UI
- 저장에 외형 포함
- 마을 레벨 해금으로 옵션이 늘어난다

### 주의점

- **스프라이트가 코드 생성이라 색 변형이 싸다**(ADR 0009). 대신 **캐시 키에 외형을 넣어야 한다** —
  지금 캐시는 종류별로만 나뉘어 있어 그대로 두면 모든 건물이 마지막 외형으로 그려진다.
- 도형 폴백도 외형을 반영해야 시각적으로 일관된다.

### 테스트

- 외형 저장 왕복
- 캐시 키가 외형별로 분리된다(같은 종류 다른 색이 각각 그려진다)
- 해금되지 않은 옵션이 거부된다

**완료 기준**: 지은 집의 지붕 색을 바꿀 수 있고, 새로고침해도 남는다.

## Phase 7 — 밸런스 3차 (마을 레벨 11~20)

**목적**: 새 콘텐츠를 진행 축에 얹는다. ADR 0011은 레벨 6~10을 **편의**로 채우면서 "진짜 새로움은
로드맵 03의 콘텐츠가 맡는다"고 남겼다. 그 약속을 지키는 Phase다.

### 작업

- `LEVEL_THRESHOLDS`·`LEVEL_UNLOCKS`를 20까지 확장 — 이번에는 **콘텐츠 해금**이다
  (동굴 개방, 고급 도구, 직업 종류, 방어 시설, 외형 옵션)
- `MAX_VILLAGE_LEVEL` 상향, 1차 목표 문구 갱신
- 봇 통과 플레이를 레벨 20까지 확장하고 구간별 소요 시간 측정
- 후반 반복 노동 완화

### 주의점

- **봇이 새 시스템을 실제로 쓰지 않으면 측정이 거짓이 된다.** 로드맵 02 Phase 6에서 봇이 평탄화를
  하지 않아 12분에 레벨 3에 머물렀던 것과 같은 함정이다. 맵 전환·직업 배정·야간 방어를 봇 로직에
  넣은 뒤에 재야 한다.
- 봇 5분이 사람 40~60분이라는 환산이 기준이다. 레벨 20이 봇 15분을 넘으면 사람에게는 너무 길다.

### 테스트

- 여러 시드에서 레벨 20 도달
- 구간별 소요 시간이 앞 구간보다 지나치게 길어지지 않는다
- 저장 왕복을 포함해도 도달한다

**완료 기준**: 처음 실행해서 레벨 20까지 막힘 없이 플레이된다.

**ADR 후보**: 레벨 11~20의 해금 곡선(**ADR 0011의 후속**).

## 2. 이 로드맵 범위 밖

- **날씨·계절** — 기획서 8절 제외 항목이다. 낮밤은 Phase 4·5의 전제라서 넣지만, 날씨와 계절은
  그것을 필요로 하는 시스템이 없다. 화면 효과만 늘고 규칙은 늘지 않는다. 다음으로 미룬다.
- **지형 조각 장식 콘텐츠(정원·연못)** — 기획서 9절이지만 순수 장식이라 진행 축에 얹히지 않는다.
- **자유 조형 건축** — 기획서 5.3이 명시적으로 배제한다. 이 게임의 정체성 자체다.
- **스토리·대사·컷신** — 기획서 2절·7절이 배제한다.
- **멀티플레이**, **모바일 터치 조작** — 기획서에 없다.

## 3. 미해결 항목

- **저장 마이그레이션 정책** — 이 로드맵은 형식을 세 번 바꾼다(다중 맵·시각·직업/외형). ADR 0008의
  "버전이 다르면 읽지 않는다"를 그대로 두면 플레이어 마을이 세 번 날아간다. **Phase 1 착수 시점에
  결정하고 ADR 0008을 개정한다.**
- **전투의 깊이** — Phase 5 착수 시점에 결정한다. 이 로드맵에서 가장 크게 벌어질 수 있는 항목이다.
- **성능 예산** — 맵 둘 + 주민 40여 명 + 몬스터 + 시간대 색조가 겹친다. 지금 60fps인 것이 유지될지
  Phase마다 확인한다(`test/performance.test.ts` 확장).
- **코드 생성 에셋의 한계** — 동굴·몬스터·직업 표현까지 코드로 그리다 보면 ADR 0009의 방식이
  버거워지는 지점이 온다. 그때 외부 에셋 도입을 ADR로 판단한다.
- **저장 슬롯** — 여전히 하나다(ADR 0008). 콘텐츠가 늘면 "다른 마을을 시험해 보고 싶다"가 생길 수
  있다. 필요해지면 키 접미사로 늘린다.
