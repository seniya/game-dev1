# 타운빌더 개발 로드맵 04 — 내보내고, 보고, 고친다

- **선행**: `docs/plan/roadmap_01.md` (MVP), `roadmap_02.md` (완성도), `roadmap_03.md` (콘텐츠 확장) — 모두 완료
- **기획서**: `docs/plan/project.md`
- **현재 상태**: 단위 테스트 886개, 봇 통과 플레이로 세 시드 모두 마을 레벨 20 도달(12.5~13.6분).
  1차 목표인 레벨 10은 4.7분.

## 목표

로드맵 03은 게임의 **폭**을 넓혔다 — 동굴, 낮과 밤, 직업, 침입, 외형, 레벨 20까지.
그런데 그 아홉 Phase가 전부 **테스트로만 확인됐다.** 어둠도, 노을도, 몬스터도, 손상 표식도,
지붕 색도 사람 눈으로 본 적이 없다. 그리고 게임은 아직 **어디에도 올라가 있지 않다.**

| 항목 | 현재 | 이 로드맵의 목표 |
|---|---|---|
| 배포 | 워크플로는 있지만 Pages가 꺼져 있고 `main`에 병합되지 않았다 | 링크를 열면 최신 게임이 뜬다 |
| 확인 | 886개 테스트가 규칙을 지킨다. 화면은 아무도 보지 않았다 | 사람 눈으로 보고, 어긋난 것을 고친다 |
| 정보 | HUD 7개 값, 조작 안내 최대 11항목, 키 15개 | 지금 필요한 것만 보인다 |
| 후반 | 레벨 11~20이 편의 해금뿐이다 | 후반에도 **할 일**이 있다 |

**새 시스템을 크게 늘리지 않는다.** 로드맵 03이 벌여 놓은 것을 실제로 서게 만드는 것이
이 로드맵의 성격이다. 단 Phase 4는 "후반의 할 일"이라는 빈자리를 채우므로 콘텐츠에 걸친다.

---

## 0. 진행 원칙

로드맵 01~03의 원칙을 그대로 잇는다.

- **수직 슬라이스 우선** — 각 Phase가 끝날 때마다 눈에 보이는 결과물이 남는다.
- **테스트 동반** — 순수 로직은 기능 직후 단위 테스트를 작성한다.
- **되돌리기 비싼 결정은 ADR** — 배경·결정·검토한 대안·예상되는 결과를 남긴다.
- **Phase 단위 커밋**, **Phase 종료 시 `docs/state/날짜_시간.md`에 상태 기록**.
- **도형 렌더링을 지우지 않는다** — 헤드리스 테스트가 그 위에서 돈다.
- **새 상호작용은 키보드로도 닿아야 한다**(ADR 0012).
- **파생값은 저장하지 않는다** — 레벨에서 나오는 보너스, 누적 시간에서 나오는 시각,
  지형에서 나오는 통로 위치(ADR 0011·0013·0015).
- **봇이 쓰지 않는 시스템은 측정되지 않는다**(ADR 0018에서 두 번 확인했다).

여기에 이 로드맵에서 새로 지킬 것 두 가지를 더한다.

- **Phase 완료 기준에 "사람이 봤다"를 넣는다.** 로드맵 03의 아홉 Phase는 모두
  "브라우저 실제 확인은 하지 못했다"로 끝났다. 규칙은 테스트가 지키지만 **화면은 테스트가
  지키지 못한다** — 색이 안 보이거나, 표식이 건물에 가려지거나, 글자가 어둠에 묻히는 종류의
  결함은 눈으로만 찾을 수 있다.
- **고칠 것을 먼저 적고 고친다.** Phase 1의 점검은 즉흥이 아니라 목록이다. 무엇을 봤고
  무엇이 어긋났는지가 남아야, 다음에 같은 것을 다시 볼 수 있다.

## 1. 의존 관계

```
Phase 0 배포 완료
   └─ Phase 1 눈으로 확인하고 고치기
         └─ Phase 3 화면과 조작 정리

Phase 2 후반 규모 성능 (독립)

Phase 4 후반의 할 일
   └─ Phase 5 미측정 구간 측정 · 밸런스 4차
```

- **Phase 0이 맨 앞인 이유**: 이후의 확인이 전부 배포본에서 이뤄져야 한다. 로컬에서만 되는
  것과 실제 주소에서 되는 것은 다른 종류로 실패한다(경로, 자산, 저장 키).
- **Phase 1이 Phase 3의 전제인 이유**: 무엇을 정리해야 하는지는 **본 뒤에** 알 수 있다.
  지금 "정보가 많다"는 것은 코드를 읽고 내린 추정이지 화면을 보고 내린 판단이 아니다.
- **Phase 2가 독립인 이유**: 성능은 측정이 곧 작업이라 다른 Phase를 기다릴 필요가 없다.
- **Phase 5가 Phase 4 뒤인 이유**: 봇에게 새 시스템을 가르치는 일은 그 시스템이 확정된
  뒤라야 의미가 있다.

## Phase 0 — 배포 완료

**목적**: 링크를 열면 최신 게임이 뜬다. 로드맵 03 Phase 0이 준비만 하고 남겨 둔 것을 끝낸다.

### 남은 절차

로드맵 03에서 `vite.config.ts`의 `base`와 `.github/workflows/deploy.yml`까지는 만들었고,
`vite preview`로 경로가 맞는 것도 확인했다. 남은 것은 **저장소 설정과 병합**이다.

- 저장소 **Settings → Pages → Source**를 **GitHub Actions**로 바꾼다(사용자 조작).
- `dev`를 `main`에 병합한다. 44개 커밋이 밀려 있다.
- Actions 실행을 확인한다 — `npm ci` → `npm test`(886개) → `npm run build` → 배포.
- 실제 주소에서 연다: 자산 로딩, 저장/이어하기, 새로고침.

### 주의점

- **테스트가 배포를 막는 구조다.** 워크플로가 `npm test`를 먼저 돌린다. 886개가 23초 걸리므로
  배포 시간이 그만큼 늘어난다 — 그래도 깨진 배포본보다 낫다.
- 저장 키가 origin 단위로 공유된다. 같은 도메인에 다른 프로젝트를 올릴 계획이 있으면
  접두어(`townbuilder.`)를 다시 본다.
- 첫 배포 뒤 **주소를 README에 확정 표기**한다. 지금은 예상 주소만 적혀 있다.

**완료 기준**: 링크를 열면 게임이 뜨고, 새로고침해도 마을이 남는다. `main`에 올리면 자동으로 갱신된다.

## Phase 1 — 눈으로 확인하고 고치기

**목적**: 로드맵 03이 넣은 것을 **처음으로 사람이 본다.** 그리고 어긋난 것을 고친다.

### 점검 목록

테스트가 "그렸다"까지만 확인한 것들이다. 보이는지, 알아볼 수 있는지, 방해되지 않는지는
아무도 모른다.

| 대상 | 무엇을 보는가 |
|---|---|
| 동굴 어둠 | 반경 5칸이 실제로 쓸 만한가. 광맥이 어둠에 완전히 묻히지 않는가 |
| 밤과 노을 | 색조가 지형·건물 색을 죽이지 않는가. 전환이 자연스러운가 |
| 몬스터 | 주민과 한눈에 구분되는가. 밤 어둠 속에서 보이는가 |
| 손상 표식 | 지붕 위 삼각형이 다른 건물에 가리지 않는가 |
| 외형 6종 | 색이 서로 구분되는가. 밤에도 구분되는가 |
| 통로 | 지상 입구와 동굴 출구가 눈에 띄는가 |
| 떠오르는 글자·파편 | 어둠과 색조 위에서 읽히는가 |
| 시계·일자리 표시 | 한 줄에 밀어 넣은 값들이 읽히는가 |
| 하루 4분 | 사람이 느끼기에 밤이 잦은가, 드문가(ADR 0015의 미확인 값) |
| 커서 6칸 | 건축 부지를 고를 때 충분한가(ADR 0012의 판단값) |

### 작업

- 위 목록을 실제로 확인하고 **결과를 `docs/state/`에 남긴다** — 무엇이 괜찮았고 무엇이 어긋났는지.
- 어긋난 것을 고친다. 색·크기·세기 조정이 대부분일 것이고, 그중 값 하나가 ADR에 적힌
  판단값이면 ADR을 갱신한다(하루 길이는 ADR 0015, 커서 범위는 ADR 0012).
- 확인 중 발견되는 **규칙 결함**은 테스트를 먼저 쓰고 고친다. 로드맵 03에서 두 번 그랬듯
  (고를 수 없는 설계도, 막힌 문 앞) 눈으로 봐야 드러나는 것이 있다.

### 주의점

- **한 번에 다 고치려 하지 않는다.** 목록을 먼저 채우고, 고칠 것을 골라 고친다. 보면서
  고치면 무엇을 봤는지 남지 않는다.
- 스크린샷을 남길 수 있으면 남긴다. 다음 로드맵이 "그때와 달라진 것"을 비교할 수 있다.

**완료 기준**: 열 가지 점검 항목에 대한 판단이 문서로 남고, 고치기로 한 것이 고쳐졌다.

**ADR 후보**: 하루 길이 변경 시 ADR 0015 개정, 커서 범위 변경 시 ADR 0012 개정.

## Phase 2 — 후반 규모 성능

**목적**: 레벨 20 규모의 마을에서 60fps가 유지되는지 확인하고, 모자라면 고친다.

### 지금 모르는 것

`test/performance.test.ts`는 렌더러 자신의 일(컬링·순회·정렬)을 재지만 **후반 규모를 재지
않는다.** 지금 재는 것은 나무 수백 개다. 실제 후반은 이렇다.

- 건물 136채(각각 점유 영역과 손상 표식과 외형)
- 주민 132명(각자 움직이고 매 프레임 위치가 보간된다)
- 몬스터 최대 5마리
- 어둠 덮개 + 시간대 색조(화면 전체를 덮는 그리기 두 번)
- 맵 둘(떠나 있는 맵의 자원 노드도 매 스텝 흐른다)

시뮬레이션 쪽도 마찬가지다. `Population.update`는 주민 수에 비례하고, `syncAnchors`는
주민마다 일터를 찾는다. 132명 × 60Hz가 어떤 비용인지 잰 적이 없다.

### 작업

- 후반 규모 픽스처를 만든다(건물 136 · 주민 132 · 몬스터 5 · 어둠 + 색조).
- 렌더 프레임 예산과 시뮬레이션 스텝 예산을 각각 잰다. 예산은 60fps(16.7ms) 안에서 나눈다.
- 넘으면 고친다. 후보:
  - 주민 기준점 계산을 매 스텝이 아니라 시간대가 바뀔 때만
  - 엔티티 정렬 비용(매 프레임 전체 정렬) 줄이기
  - 화면 밖 주민·건물 컬링
  - 스프라이트 캐시 크기 상한(외형 6종 × 건물 9종 × 크기 조합)
- 실제 브라우저에서도 확인한다(Phase 0의 배포본에서).

### 주의점

- **가짜 컨텍스트로 재는 것은 렌더러 자신의 일뿐이다.** 실제 래스터라이즈는 브라우저 몫이라,
  화면 전체를 덮는 그리기 두 번의 비용은 브라우저에서만 드러난다.
- 최적화가 도형 폴백 경로를 깨지 않아야 한다.

**완료 기준**: 후반 규모에서 프레임 예산을 지키고, 그것을 테스트가 지킨다.

**ADR 후보**: 렌더링/시뮬레이션 예산 배분 규약.

## Phase 3 — 화면과 조작 정리

**목적**: 로드맵 03이 늘려 놓은 정보와 키를 다시 정리한다.

### 지금 상태

- **HUD 상단**: 레벨 · 주민 · 건물 · 점수/다음점수 · 일차 · 시각 · 시간대 · 일자리 —
  두 줄에 여덟 값이다. 여기에 "지금 할 일"과 1차 목표가 더 붙는다.
- **조작 안내**: 상황에 따라 최대 11항목이 한 줄에 늘어선다(로드맵 02 Phase 5가 줄여 놓은
  것이 다시 길어졌다).
- **키**: WASD · 방향키 · 1~9 · Space · Q · E · B · Esc · X · R · F · G · V · C · +/- —
  **열다섯 가지**다.
- **숫자 키가 상한에 닿았다**: 설계도 9종 = 숫자 키 9개. **다음 설계도를 더하면 고를 수 없다** —
  로드맵 03 Phase 1이 고친 결함과 똑같은 것이 다시 온다.

### 작업

- 설계도 선택을 숫자 키에서 **목록 순환**으로 바꾸거나 함께 제공한다. 상한이 사라져야 한다.
  (로드맵 03 Phase 1이 "목록 순환 키"를 적어 두고 숫자 확장으로 대신했던 항목이다.)
- HUD 정보에 우선순위를 준다 — 늘 보일 것, 상황에서만 보일 것, 접어 둘 것.
- 조작 안내를 **지금 할 수 있는 것 서너 개**로 줄인다. 나머지는 도움말 한 곳에 모은다.
- 키가 하는 일이 겹치는 곳을 다시 본다(Space가 넷을 겸한다 — 채집·수리·전투·배치 확정).
  겹침 자체는 ADR 0012의 결정이지만, **무엇이 일어날지 커서에서 미리 보이는지**는 다른 문제다.

### 주의점

- 기획서 7절이 **대사창과 컷신을 배제**한다. 도움말도 창이 아니라 화면 한쪽의 목록이어야 한다.
- 줄이는 것이 목적이지 감추는 것이 목적이 아니다. 감춘 기능은 없는 기능이 된다.
- Phase 1에서 실제로 본 뒤에 하는 것이 맞다.

**완료 기준**: 처음 보는 사람이 화면에서 지금 할 수 있는 일을 셋 이내로 찾는다.
설계도가 열 종이 돼도 모두 고를 수 있다.

**ADR 후보**: 설계도 선택 방식 변경 시 ADR 0012 개정.

## Phase 4 — 후반의 할 일

**목적**: 레벨 11~20에 **새로운 할 일**을 준다. ADR 0011과 0018이 같은 한계를 두 번 남겼다 —
후반 해금이 "같은 루프를 더 편하게" 돌 뿐이다.

### 빈자리

- **수정의 쓸모가 대장간 한 채뿐이다**(ADR 0014). 두 번째 소비처가 없으면 동굴에 다녀올
  이유가 한 번으로 끝난다.
- **요청이 두 종류뿐이다**(자재 납품·시설 건축). 후반의 주된 점수원인데 형태가 늘 같다.
- **동굴이 한 층이다.** 들어가면 늘 같은 종류의 광맥이 있다.

### 작업(고를 것)

이 중 **한둘만** 고른다. 셋을 다 하면 로드맵 03의 재판이 된다.

1. **수정을 쓰는 두 번째 자리** — 상위 도구 제작(기획서 6절이 "상위 도구 제작 가능"을 레벨
   보상으로 든다), 또는 마을 시설 강화(망루 개량 등).
2. **요청 유형 추가** — 예를 들어 "밤을 무사히 넘기기", "주민 수 채우기" 같은 상태 달성형.
   기획서 5.4가 요청을 "단순 요청"으로 제한하므로 조건 하나로 판정되는 것이어야 한다.
3. **동굴 깊이** — 더 깊은 층. ADR 0013의 맵 모델이 맵을 더 늘릴 수 있게 열려 있다.

### 주의점

- **후반에만 열려야 한다.** 앞 구간에 영향을 주면 로드맵 03 Phase 8에서 맞춰 둔 곡선이
  통째로 흔들린다.
- 무엇을 고르든 **Phase 5에서 봇이 그것을 쓰게 만들어야** 측정이 성립한다.

**완료 기준**: 레벨 11~20 구간에서 "지금 무엇을 하면 되는가"에 편의 말고 다른 답이 있다.

**ADR 후보**: 고른 항목의 설계(ADR 0011·0018의 후속).

## Phase 5 — 미측정 구간 측정 · 밸런스 4차

**목적**: 아직 아무도 재지 않은 것을 잰다. 로드맵 03이 남긴 숙제 목록이다.

### 재지 않은 것들

- **동굴** — 봇이 대장간 없이도 레벨 20에 닿으므로 수정 분포와 리스폰은 판단값이다(ADR 0014).
- **일터** — 봇이 일터를 세 번 배정하는 데 그친다. 생산 속도는 판단값이다(ADR 0016).
- **침입** — 봇이 방어 시설을 짓지 않는다. 울타리와 망루가 실제로 쓸모 있는지 모른다(ADR 0017).
- **몬스터 길찾기** — **울타리로 완전히 두르면 갇힌다.** 지금은 벽 앞에 서 있다가 해가 뜨면
  물러간다. 완전 봉쇄가 최적 전략이 되는 것을 막을지, 둘지 정해야 한다(ADR 0017이 남긴 판단).

### 작업

- 봇에 동굴 왕복(수정 채굴), 방어 시설 건축, 일터 활용을 넣는다.
- 그 상태에서 구간 시간을 다시 재고, 어긋난 값을 조정한다.
- 몬스터 길찾기: 문을 부수게 할지, 우회를 시킬지, 봉쇄를 그대로 허용할지 정하고 ADR로 남긴다.
- Phase 4가 넣은 것을 봇이 쓰게 한다.

### 주의점

- **봇을 고칠 때마다 게임이 아니라 봇이 문제일 수 있다.** 로드맵 03 Phase 8에서 두 번
  그랬다 — 평탄화 폭주는 봇의 탐색 반경 때문이었고, 주민 부족은 게임의 문 앞 규칙 때문이었다.
  둘을 구분하는 데 시간을 쓰는 편이 낫다.
- 봇이 최적 플레이라는 것을 잊지 않는다. 봇이 쉬운 것이 사람에게 쉬운 것은 아니다.

**완료 기준**: 동굴·일터·방어가 통과 플레이에 등장하고, 세 시드 모두 레벨 20에 닿는 시간이
사람 기준으로 알맞은 범위 안에 있다.

**ADR 후보**: 몬스터 봉쇄 대응(ADR 0017 개정), 밸런스 조정 결과.

## 2. 이 로드맵 범위 밖

- **날씨·계절** — 로드맵 03도 미뤘다. 그것을 필요로 하는 시스템이 아직 없다.
- **모바일·터치 조작** — 화면 크기와 UI 배치를 다시 봐야 하는 별개의 일이다. 다만 Phase 3이
  정보를 정리하면 가까워진다.
- **멀티플레이**, **자유 조형 건축**, **스토리·대사** — 기획서가 배제하거나 다루지 않는다.
- **세 번째 맵** — Phase 4에서 동굴 깊이를 고르면 걸치지만, 새 지역 자체를 여는 것은 아니다.
- **아트 교체(외부 에셋)** — 코드 생성이 아직 버틴다(ADR 0009). Phase 1의 확인 결과가
  "그림이 부족하다"로 나오면 그때 판단한다.

## 3. 미해결 항목

- **사람의 피드백을 어떻게 받을 것인가** — 이 로드맵은 "사람이 본다"를 완료 기준에 넣지만,
  그 사람이 만든 이뿐이면 처음 보는 사람의 막힘은 여전히 안 보인다. 배포 뒤 누구에게
  보여줄지는 정해지지 않았다.
- **숫자 키 상한** — 설계도 9종에서 딱 찼다. Phase 3이 다루지만, 그 전에 설계도를 더하면
  같은 결함이 다시 생긴다. **Phase 4가 설계도를 늘린다면 Phase 3을 먼저 해야 한다.**
- **저장 슬롯** — 여전히 하나다(ADR 0008). 콘텐츠가 늘어 "다른 마을을 시험해 보고 싶다"가
  생길 수 있다.
- **하루 길이와 커서 범위** — 둘 다 봇 측정에 기댄 판단값이다. Phase 1이 사람 기준으로
  확인할 첫 기회다.
