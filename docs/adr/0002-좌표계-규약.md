# ADR 0002 — 아이소메트릭 좌표계 규약

- **상태**: 확정
- **일자**: 2026-09-01
- **관련 문서**: `docs/plan/project.md` 3절·5.1절, `docs/plan/roadmap_01.md` Phase 1, ADR 0001
- **구현**: `src/core/coordinates.ts`

## 배경

로드맵 Phase 1은 좌표 변환을 첫 작업으로 두고, "타일 크기 및 좌표계 규약(원점 위치, z축 방향,
타일 픽셀 치수)"을 ADR 후보로 지목했다. 이 규약은 Phase 2(복셀 지형)부터 Phase 9까지 사실상
모든 코드가 의존하며, 나중에 바꾸면 렌더링·피킹·지형·건축 배치 판정이 동시에 깨진다.
따라서 첫 렌더링 코드를 쓰기 전에 문서로 고정한다.

세 가지를 정해야 한다: 타일의 픽셀 치수, 그리드 좌표계의 축 방향과 원점, 그리고 높이가 있는
블록들의 그리기 순서 규칙이다.

## 결정

### 1. 좌표계 세 층

| 좌표계 | 단위 | 정의 | 담당 모듈 |
|---|---|---|---|
| **그리드 좌표** `(x, y, z)` | 타일 | 게임 논리가 쓰는 좌표. 정수가 아닌 값도 허용(타일 내부 위치) | `src/core` |
| **월드 좌표** `(x, y)` | px | 카메라 변환 이전의 픽셀 좌표. 그리드 `(0,0,0)`의 윗면 중심이 원점 | `src/core/coordinates.ts` |
| **화면 좌표** `(x, y)` | CSS px | 캔버스 좌상단 기준. 월드 좌표에 카메라 이동·확대를 적용한 결과 | `src/render/Camera.ts` |

월드 좌표를 중간에 둔 이유는 투영(아이소메트릭 규약)과 카메라(팬·줌)를 분리하기 위함이다.
덕분에 `src/core`는 카메라를 모르는 순수 로직으로 남고, 카메라 교체나 줌 한계 변경이 좌표 변환에
영향을 주지 않는다.

### 2. 타일 픽셀 치수

- `TILE_WIDTH = 64`, `TILE_HEIGHT = 32` — **2:1 마름모**
- `LAYER_HEIGHT = 16` — z가 1 늘면 화면에서 16px 위로

2:1을 고른 이유는 대각선 이동이 정확히 `(±32, ±16)`의 정수 픽셀이 되어 마름모 변이 픽셀 격자에
깔끔히 맞기 때문이다. 스프라이트 없이 도형으로 그리는 MVP 단계에서도, 나중에 스프라이트로
교체할 때도 반픽셀 경계로 인한 이음새가 생기지 않는다.

`LAYER_HEIGHT`를 타일 높이의 절반(=타일 폭의 1/4)으로 둔 것은 블록이 정육면체로 보이게 하는
값이 아니라, **5레이어를 다 쌓아도 화면 점유가 과하지 않은** 값으로 고른 것이다. 최대 높이는
`4 × 16 = 64px`로 타일 폭 한 칸에 해당한다. 기획서 5.1의 깊이 제한이 5레이어이므로 이 정도가
지형 높낮이를 읽히게 하면서도 시야를 가리지 않는다.

### 3. 축 방향과 원점

```
        z (위)
        │        (0,0)
        │       ◇
   y ↙  │  ↘ x        ◇(1,0) 은 오른쪽-아래
              ◇(0,1) 은 왼쪽-아래
```

- **x축**: 화면 오른쪽-아래 방향
- **y축**: 화면 왼쪽-아래 방향
- **z축**: 화면 위쪽. `z = 0`이 최하층, 값이 커질수록 높다
- **원점**: 그리드 `(0, 0, 0)` 블록의 **윗면 중심**이 월드 `(0, 0)`

변환식:

```
worldX = (x - y) × 32
worldY = (x + y) × 16 - z × 16
```

역변환은 기준 레이어 `z`를 인자로 받는다. 한 화면 지점은 z에 따라 여러 그리드 위치에 대응하기
때문이다(높은 블록의 윗면과 낮은 블록의 윗면이 같은 픽셀에 겹칠 수 있다).

**z 방향을 위로 잡은 이유**: 기획서 5.1이 "파기"와 "쌓기"를 모두 요구한다. 깊이(파기)를 양수로
잡으면 쌓기가 음수 인덱스가 되어 배열 인덱싱이 지저분해진다. 반대로 높이를 양수로 잡으면
`z = 0..4` 배열이 그대로 지형이 되고, 파기는 값을 비우는 일, 쌓기는 채우는 일이 된다.

**원점을 윗면 중심으로 잡은 이유**: 플레이어·NPC·건물은 모두 지면 위에 서므로, 블록의 윗면이
기준일 때 "이 타일 위에 있는 것"의 위치 계산이 덧셈 없이 끝난다.

### 4. 마우스 피킹

마름모 안팎 판정을 따로 하지 않는다. 역변환으로 얻은 소수 그리드 좌표를 `Math.round`하면
그 결과가 곧 해당 지점을 품은 마름모다 — 타일 중심들이 격자를 이루므로 "가장 가까운 중심"이
"그 지점을 포함하는 마름모"와 같기 때문이다. 다각형 히트 테스트나 색상 버퍼 피킹이 불필요하다.

### 5. 그리기 순서

정렬 키는 **`(x + y)` 1순위, `z` 2순위 오름차순**이다(`compareDepth`).

같은 `x + y` 대각선 위의 블록들은 화면 x가 타일 폭(64px)만큼 떨어져 서로 겹치지 않는다.
따라서 대각선 내부에서는 순서가 화면에 영향을 주지 않으며, `z`는 순서를 결정적으로 만드는
보조 키다. 대각선이 커지면 화면 아래쪽(= 카메라에 가까움)으로 가므로, 오름차순 순회가 곧
뒤에서 앞으로 그리는 화가 알고리즘이 된다.

렌더러는 매 프레임 배열을 만들어 정렬하지 않고 **대각선을 직접 순회**해 같은 순서를 얻는다
(`WorldRenderer.render`). 수천 개 객체를 프레임마다 할당하고 정렬할 이유가 없다.

### 6. 화면 밖 컬링

뷰포트 사각형은 그리드 좌표계에서 마름모가 되므로, 정확한 범위 대신 **네 꼭짓점의 그리드
좌표를 감싸는 사각형**을 쓴다(`Camera.visibleTileRange`). 보수적이라 화면 밖 후보가 일부
섞이지만 보여야 할 타일을 빠뜨리지 않는다. z가 큰 블록은 위로 밀려 그려져 뷰포트 아래쪽 밖에
있어도 보일 수 있으므로, `z = 0` 평면과 최상단 레이어 평면 양쪽으로 범위를 구해 합집합을 취한다.

## 검토한 대안

### 타일 치수 2:1 대신 다른 비율

**정투상 3:2(예: 64×42)** 는 각도가 30도에 가까워 더 자연스럽지만, 대각선 이동이 정수 픽셀로
떨어지지 않아 타일 사이에 1px 이음새가 생긴다. Canvas 2D에서 이를 없애려면 좌표를 반올림해야
하고, 그러면 카메라 팬 중에 타일이 미세하게 떠는 지터가 보인다. 기획서 3절의 "약 30~45도"
범위에 2:1(약 26.6도 투영)이 충분히 근접하므로 정수 정합성을 택했다.

**32×16(작은 타일)** 은 화면에 더 많은 타일이 들어오지만, 5레이어 높이 표현과 블루프린트
바닥 면적(기획서 5.3)을 눈으로 구분하기에 좁다. 줌으로 해결할 문제라 판단해 64×32를 기본으로 뒀다.

### 좌표 변환에 행렬 사용

투영을 2×3 행렬로 두면 나중에 각도를 바꾸기 쉽다. 그러나 기획서 3절이 회전을 명시적으로
배제했으므로 바뀔 일이 없는 자유도이고, 행렬을 도입하면 역변환이 일반 역행렬 계산이 되어
현재의 명시적 두 줄짜리 식보다 읽기 어려워진다. 상수 곱셈으로 남겼다.

### 그리기 순서를 `x + y + z`로

등거리 투영에서 카메라 방향 깊이는 `x + y + z`이며, 복셀 렌더러에서 흔히 쓰는 키다.
그러나 우리 투영은 `LAYER_HEIGHT`가 타일 높이의 절반이라 z 방향 화면 이동이 x·y 방향과
같지 않다 — 즉 진짜 등거리 투영이 아니다. `x + y + z`를 쓰면 `(1,0,1)`과 `(1,1,0)`처럼
같은 합을 갖는 블록의 순서가 임의로 정해지는데, 이 둘은 화면에서 실제로 겹친다.
`(x + y)`를 1순위로 두면 겹치는 쌍의 순서가 항상 화면 앞뒤와 일치하므로 이쪽을 택했다.

### 깊이 정렬을 z-buffer로 (오프스크린 깊이 버퍼)

블록마다 깊이값을 쓰고 픽셀 단위로 비교하면 순서 문제가 사라진다. 그러나 Canvas 2D에는
깊이 버퍼가 없어 직접 구현해야 하고, 그건 사실상 소프트웨어 래스터라이저를 만드는 일이다.
ADR 0001이 Canvas 2D를 택한 전제와 맞지 않으므로 제외했다.

## 예상되는 결과

**얻는 것**

- 좌표 변환이 왕복 손실 없는 순수 함수 4개(`gridToWorld`, `worldToGrid`, `worldToTile`,
  `compareDepth`)로 정리돼, 단위 테스트로 규약 위반을 즉시 잡을 수 있다.
- 피킹이 반올림 한 번으로 끝나 마우스 상호작용 비용이 사실상 0이다.
- 정렬 없이 대각선 순회로 그려 프레임당 할당이 없다.

**감수하는 것**

- `LAYER_HEIGHT`를 바꾸면 컬링 여유(`padY`)와 지형 높이 체감이 함께 달라진다.
  `coordinates.ts`의 상수 한 곳이지만 시각 밸런싱을 다시 봐야 한다.
- 컬링 범위가 보수적이라 화면 밖 후보를 일부 훑는다. 48×48 맵에서는 무시할 수준이고,
  맵이 커지면 대각선 순회 범위를 그리드 경계로 먼저 자르는 최적화가 가능하다.

**Phase 6에서 다시 봐야 할 지점**

현재 정렬 규칙은 **한 타일을 차지하는 1레이어 높이 블록**을 전제한다. 기획서 5.3의 건물은
여러 타일을 점유하고 여러 레이어보다 높으므로, 단일 `(x, y, z)` 키로는 순서를 정할 수 없다.
Phase 6에서 점유 영역(footprint) 기반 정렬을 별도로 도입해야 하며, 나무(Phase 4)도 같은 문제를
갖는다. 이 규약은 그때 확장되지만, 지형 블록에 대한 위 규칙 자체는 유지된다.
