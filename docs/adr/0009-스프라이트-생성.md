# ADR 0009 — 스프라이트를 파일 대신 코드로 생성한다

- **상태**: 확정
- **일자**: 2026-09-02
- **관련 문서**: `docs/plan/roadmap_02.md` Phase 2, ADR 0001, ADR 0002
- **구현**: `src/render/sprites.ts`, `WorldRenderer.setSprites`

## 배경

로드맵 02는 "아트 리소스 조달"을 Phase 2 착수 전 결정 사항으로, 그리고 **가장 먼저 막히는
지점**으로 적어 뒀다. 선택지는 셋이었다: 이미지를 직접 제작한다, 에셋 팩을 가져온다,
코드로 생성한다.

이 프로젝트는 런타임 의존성이 0개이고(ADR 0001) 외부 파일을 가져올 수 없는 환경에서
개발된다. 동시에 MVP 내내 "색상 도형"으로 그려 왔고, 그 도형 렌더링 위에서 렌더러 테스트
40여 개가 돌고 있다.

## 결정

**스프라이트를 코드로 그려 오프스크린 캔버스에 캐시한다.** 이미지 파일을 쓰지 않는다.

```
createSpriteSet() → 종류별 Sprite { image, width, height, offsetX, offsetY }
WorldRenderer.setSprites(set | null)
```

### 1. 왜 생성인가

- **파일이 필요 없다.** 에셋 조달이라는 외부 의존을 없앤다. 런타임 의존성 0개도 유지된다.
- **도형보다 훨씬 세밀하다.** 얼룩·결·명암·지층선·기와·문처럼 매 프레임 그리기에는 비싼
  표현을 **한 번만 그려 두고** 붙여 넣는다.
- **좌표 규약과 어긋날 수 없다.** 스프라이트 치수를 `TILE_WIDTH`·`LAYER_HEIGHT`(ADR 0002)에서
  직접 계산하므로, 규약을 바꾸면 그림도 함께 따라온다. 외부 이미지였다면 규약과 그림이 어긋나
  이음새가 생겼을 것이다.
- **결정적이다.** 얼룩 위치를 `sin` 기반 해시로 정해 실행마다 같은 그림이 나온다.
  스크린샷 비교가 가능하다.

### 2. 2배 크기로 만들어 두고 줄여 그린다 (`SPRITE_SCALE = 2`)

기본 크기(타일 64×32)로 만들면 확대했을 때 흐려진다. 2배로 만들면 줌 3배까지 견딘다.
메모리는 스프라이트 수십 장이라 문제되지 않는다.

### 3. 도형 경로를 지우지 않는다

`setSprites(null)`이면 기존 도형 그리기가 그대로 돈다. 이유는 셋이다.

- **헤드리스 테스트가 그 위에서 돈다.** node에는 `OffscreenCanvas`도 `document`도 없어
  `createSpriteSet()`이 null을 돌려주고, 렌더러 테스트 40여 개가 도형 기록을 검증한다.
  스프라이트를 넣은 뒤에도 기존 테스트가 **한 줄도 바뀌지 않고** 통과한다.
- 캔버스를 만들 수 없는 브라우저 설정에서도 게임이 돌아야 한다.
- 도형은 규약의 기준이기도 하다. 스프라이트가 도형과 다른 위치에 그려지면 그것이 버그다.

### 4. 건축 중 연출만 도형으로 남긴다

반투명 골조·먼지·진행 게이지는 진행도에 따라 매 프레임 달라진다. 캐시할 대상이 아니므로
스프라이트 경로에서도 도형으로 그린다.

### 5. 캐시 키

블록 타입·손상 단계·건물 외형과 면적·색상값으로 캐시한다. **주민 색은 30도 단위로 묶는다** —
주민마다 캔버스를 만들면 인구가 늘수록 메모리가 는다. 12가지면 서로 구분하기에 충분하다.

## 검토한 대안

- **이미지 파일 + 아틀라스**: 표현의 상한이 가장 높다. 그러나 에셋 조달이 선행 과제가 되고,
  비동기 로딩·실패 처리·규약과 그림의 어긋남이 모두 새 문제로 들어온다. 아트를 사람이
  그리기로 하면 그때 이 결정을 뒤집는다 — `SpriteSet` 인터페이스만 구현하면 되므로
  렌더러는 손대지 않는다.
- **도형을 더 정교하게 그리기(캐시 없이)**: 얼룩 70개를 매 타일 매 프레임 그리면 그대로
  프레임 비용이 된다. 캐시가 있어야 성립하는 표현이다.
- **CSS/SVG 스프라이트**: 캔버스에 그리려면 결국 이미지로 변환해야 하고, SVG 래스터화는
  비동기다. 이득이 없다.

## 예상되는 결과

**얻는 것**: 파일 없이 화면이 게임처럼 보인다. 지형에 질감이 생기고, 건물에 지붕 결과 문이
생기고, 철광석 광맥이 돌 광맥과 한눈에 구분된다. 도형 폴백이 남아 테스트와 안전망이 유지된다.

**감수하는 것**:
- 표현의 상한이 "코드로 그릴 수 있는 것"에 묶인다. 손으로 그린 픽셀아트만큼 개성 있는 그림은
  나오지 않는다.
- 스프라이트를 고치려면 코드를 고쳐야 한다. 아트 반복 주기가 이미지 파일보다 느리다.
- 캐시가 메모리에 남는다. 지금은 수십 장이라 무시할 수준이지만, 종류가 크게 늘면 상한을
  둬야 한다.

## 이 결정으로 드러난 것

스프라이트를 넣으면서 **오브젝트에 광맥 종류 정보가 없다는 것**을 발견했다. 도형으로 그릴
때는 돌 광맥과 철광석 광맥을 같은 그림으로 그리고 있었고(색 하나 차이도 없었다), 아무도
알아채지 못했다. `Entity`에 `iron` 필드를 더해 구분했다. 표현을 올리면 데이터의 빈틈이
드러난다는 흔한 사례다.
