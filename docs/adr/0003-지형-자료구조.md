# ADR 0003 — 지형 자료구조: 높이맵

- **상태**: 확정
- **일자**: 2026-09-01
- **관련 문서**: `docs/plan/project.md` 5.1절·5.2절, `docs/plan/roadmap.md` Phase 2, ADR 0002
- **구현**: `src/core/Terrain.ts`, `src/core/terrainGen.ts`, `src/core/picking.ts`

## 배경

로드맵 Phase 2는 지형 자료구조를 "3D 배열 vs 높이맵 + 타입맵"의 선택으로 남겨 뒀다.
이 선택을 가르는 질문은 하나였다 — **오버행(위에 블록이 있고 아래가 빈 형태)과 동굴을
지형으로 표현할 것인가**. 기획서 5.1은 파기로 생긴 "빈 공간"을 허용하지만 그것이
아래로 파인 구덩이인지 천장이 있는 공간인지 명시하지 않았고, 5.2절이 채집 구역으로
"동굴"을 언급하지만 그것이 별도 맵인지 지형 지물인지도 불명확했다.

**결정 사항으로 확인된 방침: 동굴은 별도 맵으로 다룬다.** 즉 지형은 오버행을 표현할
필요가 없다.

## 결정

**높이맵 + 칸별 타입맵**을 쓴다. 각 열(column)이 갖는 값은 **쌓인 블록 개수 하나**이고,
그 아래는 빈틈 없이 꽉 찬 것으로 본다.

```
heights[y * width + x]                      → 그 열의 블록 수 (0 ~ 5)
types[(y * width + x) * MAX_LAYERS + z]     → 칸별 블록 타입
```

둘 다 `Uint8Array`다. 32×32 맵이면 1KB + 5KB로, 배열 하나가 CPU 캐시에 그대로 들어간다.

`z >= heights[...]`인 칸의 타입 값은 의미가 없으며 항상 `EMPTY`로 읽힌다. 즉 **어떤 칸이
차 있는지는 오직 `heights`가 결정하고**, `types`는 차 있는 칸의 재질만 말한다. 이 분리가
이 설계의 핵심이다.

### 이 제약에서 따라오는 것들

| 연산 | 높이맵에서의 정의 |
|---|---|
| 파기 | 항상 열의 **맨 위** 블록 제거. `heights` 1 감소 |
| 쌓기 | 항상 열의 **맨 위**에 얹기. `heights` 1 증가 |
| 깊이 제한 | `heights <= MAX_LAYERS` 한 줄로 강제 |
| 평탄도 판정 | 영역 내 `heights`가 모두 같은지 비교. 높이 0은 지면이 없는 자리이므로 거부 |
| 표면 조회 | `types[column * MAX_LAYERS + height - 1]` |

"어느 블록을 파는가"를 따로 판정할 필요가 없어진다는 점이 특히 크다. 3D 배열이라면
클릭 지점에서 시선 방향으로 광선을 진행시켜 첫 번째 채워진 칸을 찾아야 하지만,
높이맵에서는 열이 결정되면 대상 블록도 결정된다.

### 마우스 피킹

높이가 있는 지형에서는 한 화면 지점이 여러 열에 대응한다 — 언덕 윗면과 그 뒤 낮은 땅의
윗면이 같은 픽셀에 겹칠 수 있다. 그래서 `pickSurfaceTile`은 z 평면을 위에서 아래로 훑으며
"그 평면에 해당하는 열이 그만큼 높은가"를 검사한다. 위에서부터 훑으므로 먼저 걸리는 것이
화면상 가장 앞에 있는 표면이다.

이 방식은 측면 벽을 클릭한 경우에도 그 벽의 주인 열을 찾아낸다. z가 1 줄면 후보 열이
대각선으로 반 칸씩 뒤로 물러나므로, 벽면 픽셀은 아래 평면에서 벽의 주인 열에 도달한다.
레이어가 5개뿐이라 최대 5회 반복으로 끝난다.

### 측면 렌더링

카메라를 향하는 면은 `+x` 쪽(윗면의 동-남 변)과 `+y` 쪽(남-서 변) 둘뿐이다. 각 면은
**이웃 열보다 높은 만큼만** 그린다. 따라서 평지에서는 측면 비용이 0이고, 지형이
울퉁불퉁할 때만 늘어난다. 노출된 부분은 레이어 단위로 나눠 각 레이어의 블록 색으로
칠해 흙/돌/철광석 층이 드러난다 — 파고 내려갈 단서를 화면에 주려는 의도다.

높이맵이 오버행을 허용하지 않으므로 이 방식은 화면을 빈틈 없이 덮는다. 인접한 두 열에서
한쪽 벽의 아래 변이 다른 쪽 윗면의 위 변과 정확히 일치하기 때문이다(타일 폭 64, 높이 32,
레이어 16이라는 ADR 0002의 정수 관계 덕분이다).

## 검토한 대안

### 3D 배열 (`width × height × 5`의 채움 여부 배열)

오버행·공중 블록·동굴을 모두 표현할 수 있다. 대가는 세 가지다.

1. **파기/쌓기 대상 판정이 광선 진행으로 바뀐다.** 클릭 지점에서 시선을 따라가며 첫
   채워진 칸을 찾아야 하고, 쌓기는 "어느 면에 붙일지"까지 정해야 한다.
2. **렌더링에서 가려진 면 판정이 복잡해진다.** 높이맵에서는 이웃 높이 비교 한 번이지만,
   3D 배열에서는 여섯 면 각각의 이웃 칸을 봐야 한다.
3. **평탄도 판정이 "표면 높이" 개념을 먼저 정의해야 한다.** 오버행이 있으면 한 열에
   표면이 여러 개일 수 있어, 기획서 5.3의 "평평한 빈 지면"이 무엇인지부터 애매해진다.

동굴을 별도 맵으로 다루기로 했으므로 이 비용은 쓰이지 않을 표현력에 대한 지불이 된다.

### 높이맵 + 열당 단일 타입

`types`를 열당 하나로 줄이면 메모리가 5분의 1이 된다. 그러나 흙 아래 돌, 최하층 광맥이라는
층 구성(기획서 5.1·5.2)을 표현할 수 없다. 파고 내려가며 재질이 바뀌는 것이 채굴의 동기인데
그것이 사라진다. 5KB를 아끼려고 게임 루프를 포기하는 거래라 제외했다.

### 층 타입을 깊이 규칙으로 계산 (배열 없이 `f(z)`로 결정)

"z=0은 광석, 1~2는 돌, 최상단은 흙" 같은 함수로 타입을 계산하면 `types` 배열이 아예
필요 없다. 그러나 쌓기가 성립하지 않는다 — 플레이어가 돌을 흙 위에 얹으면 규칙과 실제
지형이 어긋난다. 기획서 5.1이 쌓기를 명시하므로 제외했다.

## 예상되는 결과

**얻는 것**

- 파기·쌓기·평탄도 판정이 모두 정수 비교 수준으로 끝난다. Phase 6 건축의 전제 조건인
  `isFlatArea`가 높이 비교 이중 루프 하나다.
- 오버행이 구조적으로 불가능하므로 "떠 있는 블록"이나 "천장만 남은 지형" 같은 잘못된
  상태를 애초에 만들 수 없다. 검증 코드가 필요 없다.
- `Uint8Array` 두 개라 세이브/로드(미결 항목)를 붙일 때 직렬화가 자명하다.
- 측면을 이웃 높이 차이만큼만 그려 평지에서 렌더 비용이 윗면 하나로 수렴한다.

**감수하는 것**

- **오버행·동굴·아치를 지형으로 만들 수 없다.** 동굴은 별도 맵으로 가므로 MVP 범위에서는
  제약이 아니지만, 나중에 지형 자체에 천장을 넣고 싶어지면 이 결정을 되돌려야 한다.
  되돌리는 비용은 크다 — `Terrain`의 공개 API(파기/쌓기/평탄도/표면 조회)와 렌더러의
  측면 판정, 피킹이 모두 바뀐다.
- 열당 타입 배열이 항상 `MAX_LAYERS`칸 잡히므로, 얕은 열에서는 쓰이지 않는 칸이 남는다.
  32×32 맵에서 5KB라 무시했다.

**측정한 성능** (Chrome 헤드리스, 1280×800, 32×32 맵)

- 줌 1.73배: 윗면 812개 + 측면 351개를 매 프레임 다시 그려 **60fps 유지**
- 로드맵이 ADR 후보로 지목한 오프스크린 캔버스 캐시나 변경 영역 재그리기는 **도입하지
  않는다.** 필요하지 않은 최적화를 넣으면 파기·쌓기로 지형이 바뀔 때 캐시 무효화 버그가
  생길 여지만 만든다. Phase 9의 성능 점검에서 실제로 프레임이 떨어질 때 다시 판단한다.

**시각적으로 유의할 점**

ADR 0002에서 `LAYER_HEIGHT`를 타일 높이의 절반으로 잡았기 때문에, 두 레이어 올라간 열은
화면에서 정확히 한 타일 뒤에 있는 열과 겹쳐 보인다. 한 레이어 차이는 명확히 읽히지만
두 레이어 계단은 모호할 수 있다. 실제로 혼란을 준다면 `LAYER_HEIGHT`를 타일 높이의 절반이
아닌 값으로 바꾸는 것이 해법이며, 그것은 ADR 0002의 개정 사항이다.
