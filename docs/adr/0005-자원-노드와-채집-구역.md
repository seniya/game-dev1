# ADR 0005 — 자원 노드와 채집 구역 모델

- **상태**: 확정
- **일자**: 2026-09-01
- **관련 문서**: `docs/plan/project.md` 5.2절, `docs/plan/roadmap.md` Phase 4·Phase 8
- **구현**: `src/core/zones.ts`, `src/core/resourceNodes.ts`, `src/sim/ResourceField.ts`, `src/core/items.ts`

## 배경

기획서 5.2는 채집 구역을 "초원 → 숲 → 산악 → 동굴 순으로 상위 자원 등장"으로만 규정하고,
구역의 물리적 형태를 명시하지 않았다. 동굴은 별도 맵으로 가기로 했으므로(ADR 0003) 단일 맵에
세 구역을 어떻게 배치할지 정해야 했다. Phase 8이 이 구역을 마을 레벨로 단계 개방하므로,
구역 모델은 Phase 4가 아니라 Phase 8의 요구까지 함께 만족해야 한다.

## 결정

### 1. 구역은 마을 중심에서의 거리로 나눈다

체비쇼프 거리(`max(|dx|, |dy|)`)를 써서 초원(0~7) → 숲(8~12) → 산악(13~) 세 겹의 사각 띠로
나눈다. 지형 종류나 별도 구역 맵을 두지 않는다.

**근거**:
- **설명이 필요 없다.** "멀리 갈수록 위험하고 좋은 자원"은 규칙을 읽지 않아도 이해된다.
- **Phase 8의 단계 개방이 반지름 하나로 끝난다.** 마을 레벨이 오르면 접근 가능 반지름을
  늘리면 된다. 구역별 플래그나 영역 목록을 관리할 필요가 없다.
- 체비쇼프 거리를 쓰면 경계가 사각 띠가 되어 아이소메트릭 화면에서 **마름모 띠**로 보인다.
  유클리드 거리(원형 경계)는 타일 격자와 결이 맞지 않아 경계가 지글거린다.

### 2. 자원은 지형이 아니라 별도 노드다

나무·돌 광맥·철광석 광맥은 지형 블록이 아니라 칸 위에 놓인 오브젝트다.
`ResourceField`가 `y * width + x` → 노드 Map으로 보관한다.

**근거**: 노드는 맵 전체에 비해 희소하고(수백 개), 질문은 항상 "이 칸에 노드가 있나?"다.
배열(1024칸)을 훑는 대신 Map 조회로 끝난다. 또 지형과 분리해 두면 노드를 부순 뒤 같은 칸의
지형을 파는 일이 자연스럽게 성립한다.

**지형에도 철광석이 있다는 점은 의도한 중복이다.** 지형 최하층 광맥(ADR 0003)은 "파고 내려가
얻는" 경로, 산악의 광맥 노드는 "멀리 가서 얻는" 경로다. 기획서 5.1과 5.2가 각각 채굴을
언급하므로 둘 다 남겼다.

### 3. 노드는 결정적으로 배치하고, 설 수 있는 칸에만 놓는다

`hashNoise(x, y, seed)`로 배치하므로 같은 시드는 같은 맵을 만든다. 뚫린 칸에는 놓지 않는다 —
공중에 뜬 나무를 막고, 플레이어가 인접할 수 없는 노드를 없애기 위함이다.

### 4. 채집은 내구도 × 도구 등급

타격 한 번에 `tierSpeedMultiplier(tier)`만큼 내구도가 깎이고, 0이 되면 자원을 드롭하고
리스폰 타이머가 돈다. 등급이 높으면 더 적은 타격으로 부순다(기획서 5.2의 "채집 속도↑").

리스폰 시간은 나무 25초 < 돌 광맥 40초 < 철광석 광맥 70초로 두었다. 상위 자원이 귀해야
마을 레벨 진행(기획서 6절)에 의미가 생긴다. **수치는 Phase 9 밸런싱 대상이며 서열만 고정했다.**

### 5. 아이템을 블록과 별개 타입으로 분리

`ItemType`(목재/돌/철광석/흙)을 `BlockType`(빈칸/흙/돌/철광석)과 따로 두고 양방향 변환 함수를
제공한다.

**근거**: 목재는 지형에 존재하지 않고, 빈칸은 아이템이 될 수 없다. 또 **철광석은 아이템이지만
지형에 되놓을 수 없다** — 이 비대칭을 한 타입으로 표현하려면 어느 쪽이든 "쓰이지 않는 값"이
생긴다. Phase 5의 인벤토리와 Phase 6의 블루프린트 자재 목록, Phase 7의 납품 요청이 모두
`ItemType`을 쓴다.

## 검토한 대안

- **구역을 지형 종류로 표현** (초원=풀, 숲=나무 지형, 산악=암반): 지형 자료구조에 구역 정보를
  넣어야 하고, Phase 8의 개방이 지형 재생성이 되어 플레이어가 만든 변형을 잃는다. 제외.
- **구역을 사람이 그린 영역 데이터로**: 손으로 배치하면 밸런싱이 정밀해지지만, 맵이 하나뿐인
  MVP에서 데이터 파일과 편집 도구를 만드는 비용이 이득을 넘는다. 제외.
- **노드를 배열로 보관** (`width × height` 배열): 조회는 O(1)로 같지만 32×32에서 1024칸 중
  수백 칸만 쓰므로 메모리가 낭비되고, "모든 노드 훑기"(리스폰 갱신, 렌더링)가 빈 칸까지 훑는다.
  Map이 노드 수에 비례해 돈다. 제외.

## 예상되는 결과

**얻는 것**: Phase 8의 구역 개방이 반지름 비교 한 줄이 된다. `ResourceField.addNode`가 있어
개방 시점에 노드를 심는 방식도 가능하다. 아이템 타입 분리로 Phase 5~7이 블록 개념을 몰라도 된다.

**감수하는 것**:
- 구역이 마을 중심 기준이므로 **마을이 커져도 구역 경계는 움직이지 않는다.** 마을이 초원을
  다 덮으면 채집을 위해 항상 밖으로 나가야 한다 — 의도한 동선이지만, 이동 거리가 지루해지면
  Phase 9에서 반지름을 조정한다.
- 맵이 32×32라 산악 띠가 좁다(거리 13~15). 상위 자원이 부족하면 맵을 키우거나
  `FOREST_RADIUS`를 줄이는 것이 조정 수단이다.
