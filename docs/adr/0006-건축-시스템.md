# ADR 0006 — 건축 시스템과 블루프린트 데이터

- **상태**: 확정
- **일자**: 2026-09-01
- **관련 문서**: `docs/plan/project.md` 5.3절, `docs/plan/roadmap.md` Phase 6, ADR 0002
- **구현**: `src/core/blueprints.ts`, `src/sim/Buildings.ts`, `src/ui/BuildPanel.ts`

## 배경

기획서 5.3의 완성형 건축은 이 프로젝트의 핵심 차별점이다. 로드맵은 블루프린트 데이터를
"JSON 데이터 파일 vs 코드 상수" 중 무엇으로 둘지를 ADR 후보로 남겼다. 함께 정해야 할 것이
두 가지 더 있었다: 여러 칸을 점유하는 건물의 깊이 정렬(ADR 0002가 한계로 남긴 항목), 그리고
커서와 점유 영역의 관계.

## 결정

### 1. 블루프린트는 코드 상수 (`src/core/blueprints.ts`)

**근거**:
- **타입이 붙는다.** 자재 목록의 `ItemType`, 외형의 `BuildingStyle`이 컴파일 시점에 검증된다.
  JSON이면 런타임 파싱과 검증 코드를 따로 써야 하고, 오타가 게임을 켠 뒤에야 드러난다.
- **로딩 단계가 없다.** JSON은 `fetch`나 번들 임포트가 필요하고, 실패 처리 경로가 생긴다.
- **항목이 5개다.** 데이터 파일이 이득을 내는 규모(수십~수백 항목, 비개발자가 편집)가 아니다.

MVP를 넘어 항목이 늘고 밸런싱을 코드 수정 없이 하고 싶어지면 그때 JSON으로 옮긴다.
`BLUEPRINTS` 배열 하나가 유일한 정의 지점이므로 옮기는 비용은 작다.

### 2. 여러 칸 건물은 **가장 앞쪽 칸** 기준으로 정렬

ADR 0002의 깊이 정렬은 한 타일·1레이어 블록을 전제했다. 건물은 점유 영역의 최대 코너
`(x + width - 1, y + depth - 1)`를 정렬 키로 쓴다.

**근거**: 그 칸보다 `x + y`가 큰 지형은 나중에 그려져 건물을 정상적으로 가리고, 작은 지형은
먼저 그려져 건물에 가려진다. 점유 영역 내부의 지형은 어차피 건물이 덮으므로 순서가 문제되지
않는다. 즉 **건물 하나를 한 덩어리로 취급하면서도 지형과의 앞뒤 관계가 맞는** 가장 단순한 규칙이다.

건물끼리 겹치는 경우는 없다 — 점유가 배타적이기 때문이다.

### 3. 커서는 점유 영역의 중앙

`placementOrigin`이 커서를 중앙으로 삼아 좌상단을 역산한다. 좌상단을 기준으로 하면 3×2 건물이
커서에서 한 칸 이상 떨어져 보여 배치 감각이 어긋난다.

### 4. 자재는 인벤토리와 창고 합산, 소모는 인벤토리 우선

기획서 5.3의 "필요 자재가 인벤토리/창고에 있으면"을 그대로 따른다(`Game.totalHeld`/`consume`).
소모는 인벤토리를 먼저 비운다 — 손에 든 것을 먼저 쓰는 편이 직관적이고, 창고를 예비로 남긴다.

### 5. 배치 판정은 세 조건, 실패 이유를 값으로 돌려준다

평탄한 지면(`Terrain.isFlatArea`) + 자원 노드 없음 + 다른 건물과 미충돌.
`PlacementFailure`가 `outOfBounds`/`notFlat`/`nodeInWay`/`overlaps`를 구분해 돌려주므로
Phase 9의 토스트가 "여기는 평탄하지 않습니다" 같은 구체적 안내를 할 수 있다.

**자재 부족과 배치 불가를 구분한다.** 미리보기의 유효/무효는 둘을 합쳐 판단하지만
(`ghost().valid`), 착공 실패 결과는 `noMaterial`과 `badPlacement`로 나뉜다.

### 6. 점유 칸은 별도 Map으로 관리

`Buildings`가 `y * width + x` → 건물 번호 Map을 따로 둔다. 건물 목록을 훑어 점유를 판정하면
파기·쌓기·미리보기가 매 프레임 O(건물 수 × 면적)을 돌게 된다.

### 7. 건축은 자재 소모 후 짧은 시간, 취소는 없다

확정 즉시 자재를 소모하고 3~5초(면적에 비례) 뒤 완공된다. 건축 중에도 자리를 점유해 다른
건물이 겹치지 못한다. **취소 기능은 두지 않았다** — 기획서에 없고, 자재 환불 규칙(전액/일부)을
정해야 하는 새 결정이 생긴다. 필요해지면 Phase 9에서 다룬다.

## 검토한 대안

- **JSON 데이터 파일**: 위 1번 근거로 제외. 다만 항목이 늘면 재검토한다.
- **건물을 지형 블록으로 표현**(건물 = 특수 블록 쌓기): 기획서 5.3이 명시적으로 "칸 단위 조립
  과정은 생략"을 요구하므로 규격 위반이다. 또 높이맵(ADR 0003)에 건물 개념을 섞으면 파기·쌓기
  규칙이 건물을 특수 취급해야 한다. 제외.
- **깊이 정렬을 건물의 모든 점유 칸에 대해 조각내어 그리기**: 정확도는 최고지만 건물 스프라이트를
  타일 단위로 잘라야 한다. 도형으로 그리는 단계에서 얻을 이득이 없다. 제외.

## 예상되는 결과

**얻는 것**: 블루프린트 추가가 배열에 항목 하나 넣는 일이 된다(해금 레벨·자재·면적·외형 포함).
Phase 7의 시설 요청은 `Buildings.hasCompleted(blueprintId)`, Phase 8의 마을 레벨은
`Buildings.completedCount`와 `sumCompleted`로 끝난다.

**감수하는 것**:
- 건축 취소가 없어 잘못 놓으면 자재를 잃는다. 미리보기로 사전 확인이 가능하므로 MVP에서는
  감수하되, 플레이 중 실제로 문제가 되면 철거(일부 환불)를 Phase 9에서 넣는다.
- 커서 중앙 기준이라 3×2 건물은 좌우 비대칭으로 놓인다(`floor((width-1)/2)`). 회전이 없으므로
  (기획서 3절) 방향을 바꿔 놓을 수는 없다.
