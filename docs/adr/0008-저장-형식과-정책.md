# ADR 0008 — 저장 형식과 저장 정책

- **상태**: 확정
- **일자**: 2026-09-02
- **관련 문서**: `docs/plan/roadmap_02.md` Phase 1, ADR 0003, ADR 0005
- **구현**: `src/core/save.ts`, `src/sim/SaveStore.ts`, `src/sim/SaveSession.ts`, `Game.toSave/fromSave`

## 배경

MVP는 새로고침하면 마을이 사라졌다. 로드맵 02는 지속성을 첫 Phase로 두었고, 정해야 할 것이
넷이었다: 어디에 저장할지, 어떤 형식으로 저장할지, 무엇을 저장할지, 언제 저장할지.

## 결정

### 1. localStorage에 JSON 한 덩이, 슬롯은 하나

**근거**: 저장 크기가 32×32 맵에서 약 25KB다. localStorage의 일반적 한도(5MB)에 한참 못
미치므로 IndexedDB의 비동기 API와 스키마 관리를 감수할 이유가 없다. 슬롯을 하나로 둔 것은
"여러 마을을 굴린다"는 요구가 기획서에 없기 때문이다. 슬롯이 필요해지면 키에 접미사를
붙이는 것으로 늘릴 수 있다.

### 2. 형식에 버전을 넣고, 버전이 다르면 읽지 않는다

블록 타입은 숫자, 아이템·블루프린트 식별자는 문자열 리터럴이다. **값이 바뀌면 예전 저장이
예외 없이 잘못 읽힌다** — 흙이 돌이 되고 우물이 집이 되는 식으로 조용히 어긋난다.
그래서 `SAVE_VERSION`을 첫 저장부터 넣고, 다르면 거절한다.

마이그레이션은 필요해질 때 붙인다. 지금은 "거절하고 새 게임"이 유일한 경로이며, 그때도
**저장은 지우지 않는다** — 사용자의 마을이 담긴 유일한 사본일 수 있다.

### 3. 지형은 base64, 나머지는 그대로 JSON

지형 두 배열(`heights`, `types`)이 저장의 대부분이다. 숫자 배열 JSON 대신 base64로 담으면
길이가 눈에 띄게 줄고, 자동 저장이 30초마다 반복되므로 크기가 곧 비용이다. 인코딩을 직접
구현한 이유는 `btoa`가 큰 배열에서 인자 개수 제한에 걸리고, node 테스트에서도 같은 코드가
돌아야 하기 때문이다.

### 4. 파생 자료구조는 저장하지 않고 조립 과정에서 다시 만든다

`Buildings`의 점유 맵은 건물 목록에서 파생된다. 함께 저장하면 **원본과 파생이 어긋난 저장**이
생길 수 있다. 로드는 "상태를 그대로 되살리는 것"이 아니라 **저장값으로 객체를 다시 조립하는
것**으로 정의했다.

**자원 노드는 배치까지 통째로 저장한다.** 시드로 재현할 수도 있지만, 그러면 생성 규칙을
손대는 순간 예전 저장의 노드 위치가 조용히 달라진다. 지형을 어차피 통째로 저장하므로
시드에 기대는 이득도 없다.

**진행 중인 동작은 저장하지 않는다.** 플레이어의 이동·휘두르기, NPC의 배회가 그렇다.
불러온 순간 가만히 서 있는 편이 자연스럽고, 저장 시점의 애매한 프레임을 재현할 이유가 없다.
반면 **건축 남은 시간과 노드 리스폰 시간은 저장한다** — 그것은 진행 중인 동작이 아니라
마을의 상태다.

### 5. 손상은 부위별로 다르게 다룬다

- **거절해야 하는 손상**: 지형 배열 길이 불일치, 열 높이가 상한 초과, 창고가 하나도 없음.
  그대로 읽으면 이후 모든 판정이 배열 밖을 읽거나 진행이 막힌다.
- **그 항목만 버리는 손상**: 없어진 블루프린트를 가리키는 건물, 개수가 음수인 인벤토리 슬롯,
  형식이 깨진 요청. 아이템 몇 개나 건물 하나보다 이어서 플레이하는 편이 낫다.

### 6. 자동 저장 30초 + 탭을 닫을 때, 그리고 **저장 멈춤**

자동 저장은 게임 시간 30초 간격이고, `pagehide`와 `visibilitychange`에서도 저장한다.

**"새로 시작"과 "되돌리기"는 저장을 멈춘 뒤에 페이지를 다시 연다.** 이것이 이 ADR에서 가장
비싸게 얻은 규칙이다 — 처음 구현에서는 두 조작이 **동작하지 않았다**. 저장을 지우고
`location.reload()`를 부르면, 페이지가 닫히며 `pagehide`가 현재 상태를 한 번 더 저장해
방금 지운 것을 즉시 되살렸기 때문이다. 브라우저에서 실제로 확인하다가 발견했다.

그래서 "언제 저장할지"를 `SaveSession`이라는 값 객체로 뽑아 `suspend()`를 두고, 그 상황을
단위 테스트로 고정했다.

## 검토한 대안

- **IndexedDB**: 용량이 크고 비동기라 큰 저장에 적합하지만, 25KB에는 과하다. 저장이 커지면
  (다중 맵 등) 재검토한다.
- **전체를 base64 이진 포맷으로**: 더 작아지지만 사람이 읽을 수 없어 디버깅이 어렵다.
  지형만 base64로 두는 절충이 크기와 가독성을 함께 얻는다.
- **시드 + 변경 로그만 저장**: 이론상 가장 작다. 그러나 모든 변경을 되돌릴 수 있는 형태로
  기록해야 하고, 로드가 "처음부터 다시 실행"이 되어 시간이 걸린다. 제외.
- **자동 저장만 두고 수동 저장 없애기**: 자동 저장이 충분하지만, "지금 저장됐나?"를 확인할
  수단이 없으면 사용자가 불안해한다. 상태 표시와 수동 버튼을 함께 뒀다.

## 예상되는 결과

**얻는 것**: 새로고침해도 마을이 남는다. 이후 Phase의 확인이 "새로 시작해서 다시 모으기"가
아니게 된다. 통과 플레이 봇에 저장/불러오기를 끼워 돌려도 레벨 5에 도달한다(테스트로 고정).

**감수하는 것**:
- 저장 형식이 바뀔 때마다 버전을 올려야 하고, 그때 기존 저장은 읽히지 않는다. 마이그레이션을
  붙이기 전까지는 개발 중 저장이 자주 버려질 수 있다.
- 슬롯이 하나라 실험적인 플레이를 하려면 기존 마을을 덮어쓰게 된다. "되돌리기"가 마지막
  저장으로 돌아가는 최소한의 안전장치다.
