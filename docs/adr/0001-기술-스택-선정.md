# ADR 0001 — 기술 스택 선정

- **상태**: 확정
- **일자**: 2026-09-01
- **관련 문서**: `docs/plan/project.md` 3절(시점 및 그래픽 스타일), `docs/plan/roadmap_01.md` Phase 0

## 배경

`docs/plan/roadmap_01.md`의 Phase 0은 "코드를 작성하고 실행하고 테스트할 수 있는 최소 골격"을 요구하며,
기술 스택을 미해결 항목으로 남겨두었다. 스택은 되돌리기 비용이 가장 큰 결정이므로 첫 코드를 쓰기 전에 확정한다.

기획서에서 스택 선택을 좌우하는 제약은 다음과 같다.

- **3절**: 2.5D 아이소메트릭, **카메라 회전 없는 고정 각도 + 줌만 지원**. 진짜 3D 자유 시점은 요구되지 않는다.
- **5.1절**: 지형은 `width × height × 5레이어` 복셀 그리드. 측면 벽면을 포함한 높이 표현과 **커스텀 깊이 정렬**이 필요하다.
- **로드맵 0절**: 순수 로직(좌표 변환, 지형 자료구조, 인벤토리, 레벨 계산)은 기능 구현 직후 단위 테스트를 작성한다.

즉 이 프로젝트의 난이도는 3D 렌더링이 아니라 **좌표계 규약과 복셀 자료구조의 정확성**에 몰려 있다.

## 결정

**TypeScript + Canvas 2D**를 채택한다. 도구는 Vite(개발 서버·빌드), Vitest(단위 테스트)만 쓰고 게임 엔진은 도입하지 않는다.

디렉토리 구조는 로드맵 Phase 0의 안을 그대로 따른다.

| 경로 | 책임 | 브라우저 API 의존 |
|---|---|---|
| `src/core` | 좌표 변환, 지형 자료구조, 고정 timestep 계산 등 순수 로직 | 없음 (테스트 대상) |
| `src/render` | Canvas 2D 렌더러, 카메라 | 있음 |
| `src/sim` | 게임 루프, 게임 상태 | 루프만 rAF 의존 |
| `src/ui` | DOM 오버레이 UI | 있음 |
| `test` | Vitest 단위 테스트 | 없음 (node 환경) |

핵심 규칙은 **브라우저 API에 닿는 코드와 순수 로직을 분리**하는 것이다. 예를 들어 고정 timestep의
스텝 수 계산은 `src/core/fixedTimestep.ts`의 순수 함수(`planSteps`)로 두고, `requestAnimationFrame`
연결만 `src/sim/GameLoop.ts`가 담당한다. 덕분에 테스트는 jsdom 없이 node 환경에서 돌아간다.

## 검토한 대안

### Vanilla JS + Canvas 2D

빌드 단계가 없어 셋업이 가장 빠르다. 초기화 이전 코드가 이 방식이었다.
그러나 이 프로젝트의 주된 버그원은 좌표계(그리드 x/y/z ↔ 화면 x/y)와 블록 타입 열거값이다.
`{x, y}`와 `{screenX, screenY}`를 뒤바꿔 넘기는 실수는 타입 없이는 렌더 결과가 이상해질 때까지
드러나지 않는다. 자료구조가 Phase 2(복셀 지형), Phase 5(인벤토리), Phase 6(블루프린트)에서 계속
불어나므로 타입 검사의 이득이 빌드 단계 비용을 넘는다고 판단했다.

### Phaser 3

스프라이트·입력·씬 관리·카메라 팬/줌을 기본 제공해 Phase 1·3·9가 빨라진다.
반대급부는 두 가지다. 첫째, 기획서 5.1의 복셀 지형은 측면 벽면을 포함한 **커스텀 깊이 정렬**이
필요한데 이는 엔진의 디스플레이 리스트 규칙과 싸워야 하는 작업이다. 둘째, 순수 로직 테스트에
엔진 의존성이 섞여 로드맵 0절의 테스트 원칙이 흐려진다. 카메라 팬/줌은 회전이 없으므로 직접
구현해도 행렬 하나 수준이며, 엔진이 절약해주는 양이 크지 않다.

### Three.js

복셀을 실제 3D로 그리고 `OrthographicCamera`를 고정하면 깊이 정렬을 z-buffer가 자동 처리한다.
그러나 기획서 3절이 카메라 회전을 명시적으로 배제했으므로 3D의 자유도는 쓰이지 않는다.
대신 조명·머티리얼·메시 인스턴싱·지오메트리 수명 관리가 새 부담으로 들어온다.
쓰지 않을 자유도를 위해 난이도를 올리는 선택이라 판단해 제외했다.

## 예상되는 결과

**얻는 것**

- 좌표 변환과 복셀 자료구조를 타입으로 고정해, 렌더 결과를 눈으로 확인하기 전에 오류를 잡는다.
- 의존성이 devDependencies 3개(vite, typescript, vitest)뿐이다. 런타임 의존성은 없다.
- 깊이 정렬을 직접 통제하므로 기획서 5.1의 높이 있는 지형 렌더링에서 엔진 규칙과 충돌하지 않는다.
- 테스트가 node 환경에서 돌아 빠르다(현재 23개 테스트 약 0.14초).

**감수하는 것**

- 스프라이트 아틀라스, 입력 처리, 파티클(Phase 9의 먼지 이펙트), 카메라 팬/줌을 직접 구현해야 한다.
- 빌드 단계가 생겨 브라우저에서 파일을 직접 열 수 없고 `npm run dev`가 필요하다.
- Canvas 2D는 타일 수가 늘면 드로우콜이 병목이 된다. Phase 1의 화면 밖 컬링과 Phase 2의 렌더링
  성능 전략(로드맵 ADR 후보)에서 이 지점을 다시 다룬다. 그때도 부족하면 WebGL 전환을 검토하되,
  `src/core`가 렌더러와 분리돼 있으므로 교체 범위는 `src/render`에 국한된다.

**되돌리기 비용**

렌더러 교체(Canvas 2D → WebGL 또는 Phaser)는 `src/render`만 바꾸면 되므로 비교적 싸다.
반대로 TypeScript 제거는 전 파일에 걸치므로 비싸다. 타입 도입이 더 되돌리기 어려운 쪽임을
인지하고 선택했다.
