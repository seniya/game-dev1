## 이번에 한 일

### 지형 자료구조 확정 (ADR 0003)

Phase 2를 가로막던 미결 질문은 "오버행과 동굴을 지형으로 표현할 것인가"였다.
**동굴은 별도 맵으로 간다는 방침이 정해져** 오버행 표현이 불필요해졌고, 이에 따라
**높이맵 + 칸별 타입맵**을 채택했다. 근거와 대안 검토는 `docs/adr/0003-지형-자료구조.md`에 있다.

```
heights[y * width + x]                    → 그 열의 블록 수 (0 ~ 5)
types[(y * width + x) * MAX_LAYERS + z]   → 칸별 블록 타입
```

핵심은 **어떤 칸이 차 있는지는 오직 `heights`가 결정하고, `types`는 재질만 말한다**는 분리다.
여기서 따라오는 결과:

- 파기는 항상 맨 위 블록 제거, 쌓기는 항상 맨 위에 얹기 — "어느 블록을 파는가"를 따로
  판정할 필요가 없다. 3D 배열이라면 시선 방향 광선 진행이 필요했다.
- 오버행·공중 블록이 구조적으로 불가능하므로 잘못된 지형 상태를 만들 수 없다.
- 평탄도 판정이 높이 비교 이중 루프 하나다.
- `Uint8Array` 두 개라 세이브/로드를 붙일 때 직렬화가 자명하다.

### 조작

- **좌클릭**: 파기. 파낸 블록 중 지형에 되놓을 수 있는 것만 손에 남는다(철광석은 자원이므로 제외)
- **우클릭**: 쌓기. 흙을 먼저 쓰고 없으면 돌을 쓴다
- 드래그 팬과 휠 줌은 Phase 1과 동일

### 설계상 지킨 규칙

- **측면은 이웃보다 높은 만큼만 그린다.** 평지에서는 측면 비용이 0이고 지형이 울퉁불퉁할
  때만 늘어난다. 노출 부분은 레이어 단위로 나눠 각 레이어 색으로 칠해 흙/돌/광석 층이 보인다.
- **입력과 지형을 분리했다.** `PointerControls`는 `pick` 함수를 주입받으므로 지형을 모른다.
  덕분에 Phase 1의 평지 피킹 테스트가 그대로 유효하다.
- **결정적 생성.** 시드가 같으면 같은 지형이 나와 테스트가 재현된다.

### 도중에 잡은 문제 두 건

1. **호버 하이라이트 투시** — 하이라이트를 모든 지형을 그린 뒤 마지막에 얹고 있었다.
   그 결과 하이라이트한 열을 가려야 할 앞쪽 열 위에까지 하이라이트가 올라와, 지형을
   투시하는 것처럼 보였다(구덩이 안을 가리킬 때 특히 두드러졌다). 대각선 순회 안에서
   해당 열을 그린 직후에 얹도록 바꿨다. 헤드리스 캡처를 확대해 보다가 발견했다.
2. **우클릭 드래그의 클릭 판정** — 주 버튼은 팬을 겸하므로 이동 거리로 클릭/드래그를
   가르지만, 보조 버튼은 팬을 하지 않으므로 얼마나 움직였든 놓은 자리의 클릭으로 보는 것이
   맞다. 기존 코드는 이 구분이 암묵적이었다(보조 버튼에서는 이동 거리가 누적되지 않아
   우연히 동작). 의도를 코드에 명시하고 테스트를 그 규칙으로 고쳤다.

  - 나머지: `coordinates` `Camera` `GameLoop` `fixedTimestep` `FpsCounter` `GameState` `DebugOverlay` `PointerControls`
- `npm run build` — 성공 (JS 15.3kB)
- **브라우저 실제 확인** — Chrome 헤드리스를 CDP로 몰아 확대·파기·쌓기를 재현했다.
  클릭마다 오버레이를 읽어 매번 적용되는지 확인:
  ```
  시작:    타일 (20, 20) 흙 높이 4 · 보유 없음
  클릭 1:  타일 (20, 20) 돌 높이 3 · 보유 흙 1
  클릭 2:  타일 (20, 20) 돌 높이 2 · 보유 흙 1 · 돌 1
  클릭 3:  타일 (19, 19) 돌 높이 3 · 보유 흙 2 · 돌 1
  클릭 4:  타일 (19, 19) 돌 높이 2 · 보유 흙 2 · 돌 2
  클릭 5:  타일 (19, 19) 돌 높이 1 · 보유 흙 2 · 돌 3
  ```
  구덩이가 깊어지면서 같은 화면 지점이 뒤쪽 열을 가리키게 되는 것(3번째 클릭에서 (20,20) →
  (19,19))도 표면 피킹의 정상 동작이다. 캡처를 확대해 구덩이 안 흙/돌 층과 쌓아 올린
  블록의 측면이 제대로 보이는 것을 확인했다. 60fps 유지(윗면 812 + 측면 351).

Phase 2의 완료 기준(클릭으로 땅을 파고 다시 메울 수 있고, 높낮이가 화면에 정상적으로
보인다)을 충족한다.

### 성능 판단

로드맵이 Phase 2의 ADR 후보로 지목한 "렌더링 성능 전략"(오프스크린 캔버스 캐시, 변경 영역
재그리기)은 **도입하지 않았다.** 매 프레임 전부 다시 그려도 60fps가 유지되며, 필요하지 않은
캐시를 넣으면 파기·쌓기로 지형이 바뀔 때 무효화 버그가 생길 여지만 만든다. Phase 9의 성능
점검에서 실제로 프레임이 떨어질 때 다시 판단한다. 이 판단도 ADR 0003에 기록했다.

## 다음 할 일

로드맵의 의존 관계상 Phase 2와 Phase 3은 병렬 가능하며, Phase 2가 끝났으므로 **Phase 3(플레이어와 조작)**이 다음이다.

### Phase 3 — 플레이어와 조작

- 플레이어 스프라이트 렌더링 및 지형 위 배치(**높이 반영** — `columnHeight`로 z를 정한다)
- 그리드 기반 이동(키보드), 이동 불가 지형 충돌 처리
- 도구 슬롯 선택(도끼/곡괭이/삽) 및 타격 액션
- 상호작용 대상 판정: **플레이어 인접 타일만** 채집/파기 가능

**Phase 3 시작 전에 정할 것** (로드맵에 ADR 후보로 지목되지 않았지만 결정이 필요하다):

- **이동 규칙**: 높이 차가 몇 칸까지 오를 수 있는가. 1칸까지만 오르내리게 하면 지형 변형이
  이동로 확보라는 목적을 얻는다(기획서 5.1의 "평탄화" 동기와 맞물린다). 무제한이면 지형이
  이동에 의미를 갖지 못한다. **1칸 제한을 권장한다.**
- **이동 방식**: 타일 단위 순간 이동 vs 타일 사이 보간 이동. 후자가 보기 좋고 `GameLoop`의
  `alpha` 보간이 이미 준비돼 있으나, 이동 중 상호작용 판정이 애매해진다.
- **인접 판정 범위**: 4방향(상하좌우)인지 8방향(대각선 포함)인지.

### 이후 Phase에서 다시 봐야 할 것

- **Phase 5**: `BlockStash`를 인벤토리로 대체한다. 슬롯·스택·용량 제한이 들어오면
  `main.ts`의 쌓기 우선순위(흙 → 돌) 하드코딩도 슬롯 선택으로 바뀐다.
- **Phase 6**: `Terrain.isFlatArea`가 준비됐다. 남은 것은 점유 타일 관리(건물이 이미 있는
  자리 거부)이며, 이는 지형이 아니라 건물 목록의 책임이다.
- **Phase 6**: 깊이 정렬 규칙은 여전히 한 타일·1레이어 블록 전제다. 여러 타일을 점유하는
  건물과 나무(Phase 4)는 점유 영역 기반 정렬이 따로 필요하다(ADR 0002에 명시).
- **ADR 0002 재검토 가능성**: `LAYER_HEIGHT`가 타일 높이의 절반이라, 두 레이어 올라간 열은
  화면에서 한 타일 뒤 열과 겹쳐 보인다. 한 레이어 차이는 명확하지만 두 레이어 계단은
  모호할 수 있다. 실제로 혼란을 준다면 `LAYER_HEIGHT` 변경이 해법이다.
