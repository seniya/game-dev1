### 결정한 것

- **인벤토리와 창고가 같은 클래스** — 규칙이 갈라질 이유가 없고, 둘 사이 이동(`moveTo`)을
  한 클래스 안에서 다루는 편이 안전하다. 플레이어는 8슬롯 × 20스택, 창고는 24슬롯 × 99스택.
- **스택은 부분 스택을 빈 슬롯보다 먼저 채운다** — 같은 아이템이 여러 슬롯에 흩어지지 않는다.
- **`add`는 들어가지 못한 개수를 돌려준다** — 호출부가 "전부 들어갔는지"를 알아야 채집을
  거절할지 판단할 수 있다. 반대로 `remove`는 전부-또는-전무다.
- **용량이 부족하면 행동 자체를 거절한다** — 부서질 타격인데 드롭이 다 안 들어가면 타격을
  거절하고 노드를 살려 둔다. 파고 나서 자원을 잃는 것보다 낫다. 지형 파기도 같다.
- **예치는 흙을 남긴다** — 평탄화 작업 중에 흙까지 예치되면 곧바로 다시 꺼내야 해서 번거롭다.
- **건물이 점유한 칸은 파거나 쌓을 수 없다**(`Game.isOccupied`) — 건물 아래 지형이 바뀌면
  건물이 공중에 뜨거나 묻힌다. Phase 6에서 건물 목록이 늘어나면 이 함수가 그것까지 본다.
- **자재 소모는 인벤토리 먼저, 부족하면 창고** — 기획서 5.3이 "인벤토리/창고에 있으면"이라고
  하므로 `totalHeld`/`consume`을 Phase 6 건축이 쓴다.
- **UI는 변경 번호로 갱신을 줄인다** — `Inventory.revision`이 바뀌었을 때만 슬롯 DOM을 손댄다.

창고는 시작 칸 옆에 자동으로 놓이고 `warehouse` 외형의 건물로 그려진다. Phase 6에서
블루프린트로 추가 건설이 가능해진다.

## 검증 결과

- `npm run typecheck` / `npm run build` — 통과 (JS 35.8kB)
- `npm test` — **356개 통과** (22개 파일)
  - `Inventory`(27개): 부분 스택 우선 채우기, 상한 초과 시 다음 슬롯, 여유 공간 계산,
    부분 이동, 전체 이동 제외 목록, **아무것도 들어가지 않으면 변경 번호가 오르지 않음**
  - `Game`(+11개): 창고 칸 파기/쌓기 거부, 흙을 남기는 예치, 멀어지면 입출고 불가,
    합산 자재 판정, 인벤토리 먼저 소모, 가득 찼을 때 파기·채집 거절(노드 보존)
  - `InventoryBar`(8개): 슬롯 생성, 내용 반영, **변경이 없으면 DOM을 건드리지 않음**,
    창고 근접 강조
- **브라우저 실제 확인** — 채집 → 귀환 → 예치 전체 흐름
  ```
  시작 바:      초급 삽 (1/3) | 창고: 비어 있음 — E 예치
  4칸 이동 후 벌목: 슬롯에 3 표시 (목재 3)
  6칸 되돌아옴:  창고: 비어 있음 — E 예치     ← 인접 판정 켜짐
  E 예치 후:     슬롯 비움 · 창고: 목재 3
  ```
  캡처에서 플레이어 몸통 색이 건물 벽(베이지)과 비슷해 잘 안 보이는 것을 발견하고 파란 계열로
  바꿨다.

Phase 5의 완료 기준(채집한 자원이 인벤토리 바에 보이고, 창고에 옮길 수 있다)을 충족한다.
